## 🛠️ 개발 스펙 정의
- 기술 스택·인증·데이터 저장·배포 방향의 상세 근거는 [architecture.md](./architecture.md)를 참고한다. 요약:
  - Next.js 16(App Router) + React 19 + TypeScript, AWS 배포, 별도 스테이징 없음
  - 인증: next-auth(Auth.js) v5 + AX Auth(사내 SSO) Credentials 프로바이더
  - 저장소: 자체 DB 없음, Confluence Cloud REST API(v2 우선, 일부 v1)가 유일한 저장소
  - 알림: Slack Incoming Webhook(운영 이상 감지)
- 코드 구조 원칙: `src/lib/confluence/client.ts`(Confluence REST 저수준 래퍼) → `src/lib/editor/*.ts`(도메인 로직) → `src/app/api/editor/**/route.ts`(얇은 API 컨트롤러) → `src/app/editor/**/page.tsx` + `src/components/editor/*.tsx`(화면). 도메인 계층은 `ValidationError`/`NotFoundError`/`ConflictError`/`UnauthorizedError`를 던지고, `src/lib/api-response.ts`의 `toErrorResponse()`가 공통 에러 응답으로 변환한다.
- 에디터/UI 라이브러리: TipTap(WYSIWYG 엔진, 문서 원본은 JSON으로 저장), `@sfood/ui` + Tailwind CSS(사내 디자인 시스템 — [design.md](./design.md) 참고). 이미지는 `confluence-attachment://{filename}` 스킴으로 Confluence storage format의 `<ac:image>`에 매핑한다(변환기는 자체 작성, `marked`는 더 이상 쓰지 않음).
- 실제 Confluence 쓰기는 항상 공용 서비스 계정으로만 이루어진다. 로그인한 직원의 이메일은 Confluence 신원이 아니라 content property로만 기록되는 "실제 작성자 식별자"다.

## 🧩 기능별 정의

### 기능 — 로그인 (AX Auth)
- 설명: 사내 MS 계정으로 로그인한다. AX Auth가 SSO를 대행한다.
- 입력: 없음(리다이렉트 방식 — AX Auth 로그인 페이지에서 인증 후 콜백으로 loginToken 전달)
- 출력·동작: `/api/auth/ax-callback`이 loginToken을 검증하고 next-auth 세션(이메일)을 생성, `/editor`로 이동
- 예외 상황: 토큰 누락·검증 실패 시 `/login?error=...`로 리다이렉트
- 데이터 저장 여부: 아니오 (세션은 next-auth가 관리, 별도 저장 없음)
- API 필요 여부: 예 — api-spec.md의 인증 관련 엔드포인트 참고
- 상태: 완료(기존 구현)

### 기능 — 내 문서함 조회
- 설명: 로그인한 사용자의 계정 폴더 하위 "초안"+"게시" 문서를 함께 보여주고 상태 뱃지로 구분한다. 계정 폴더(및 초안/게시 서브페이지)가 없으면 자동 생성한다. 게시해도 목록에서 사라지지 않는다.
- 입력: 세션 이메일
- 출력·동작: 문서 목록(제목, 최종 수정일, 게시 여부)
- 예외 상황: Confluence 연동 실패 시 502 + Slack 알림
- 데이터 저장 여부: 예 — data-spec.md의 "계정 폴더"/"문서" 참고
- API 필요 여부: 예 — `GET /api/editor/folder`, `GET /api/editor/documents`
- 상태: 완료 — 산출물: src/lib/editor/folder.ts, src/lib/editor/folder.test.ts, src/lib/editor/documents.ts, src/lib/editor/documents.test.ts, src/app/api/editor/folder/route.ts, src/app/api/editor/documents/route.ts, src/app/editor/layout.tsx, src/lib/editor/tag-suggestions.ts

### 기능 — 문서 전체 검색(Ctrl+K)
- 설명: 사이드바의 상시 검색(제목·태그, 클라이언트 필터)과 별개로, `Ctrl+K`/`Cmd+K`로 여는 전역 팝업에서 제목·태그·본문(TipTap 문서에서 추출한 순수 텍스트)을 함께 검색한다([Issue #7](https://github.com/sfood-pioneer-1st/sfood-it-editor/issues/7), P1-1a 후속, 2026-09-03 결정·구현). `/editor/*` 어느 화면에서든 열 수 있다. Notion의 Ctrl+K 검색 화면을 참고해 좌측 결과 목록 + 우측 미리보기의 2단 레이아웃으로 재구성했다(2026-09-03 재구성).
- 입력: 검색어(자유 텍스트, 300ms 디바운스 후 서버에 전송), "제목만" 필터 토글(클라이언트에서 결과를 다시 거름, 재조회 없음)
- 출력·동작: 일치하는 문서를 최종 수정일 기준 오늘/어제/최근 7일/이전 구간으로 묶어 좌측 목록에 표시(각 행: 상태 아이콘 + 제목 + 태그). 방향키로 강조를 옮기면 우측 패널에 그 문서의 태그·제목·본문 스니펫 미리보기가 나타난다. 클릭하거나 Enter를 누르면 해당 문서 편집 화면으로 이동
- 예외 상황: 검색 API 실패 시 오류 메시지 표시. 개인 폴더가 없으면 빈 목록. 결과가 없으면 안내 문구
- 데이터 저장 여부: 아니오(조회 전용)
- API 필요 여부: 예 — `GET /api/editor/documents/search?q=...`(사용자가 팝업을 열고 입력할 때만 호출되는 온디맨드 API — 사이드바가 매 렌더링마다 쓰는 `listDocuments()`와는 별개). 응답에 미리보기용 `snippet`(본문 중 검색어 주변 문맥, 없으면 본문 앞부분) 필드 포함
- 상태: 완료 — `listDocuments()`가 이미 문서마다 본문(`sourceDocument.doc`)을 조회하면서 제목만 쓰고 버리고 있었다는 것을 확인해 그 조회를 재사용했다(원래 우려했던 "N+1 비용을 배로 늘린다"는 문제가 실제로는 없음). `@sfood/ui`의 `Modal`은 `size`가 최대 `max-w-2xl`까지만 지원해 2단 와이드 레이아웃을 담을 수 없어 커스텀 오버레이로 대체했다(이유는 design.md "Ctrl+K 검색 팝업" 절 참고). 산출물: `docs/superpowers/tasks/P1-1a-content-search-ctrlk/{task,plan,result,test}.md`(최초 구현), `docs/superpowers/tasks/P1-1a-search-notion-style-redesign/{task,plan,result,test}.md`(Notion 스타일 재구성), src/lib/editor/documents.ts, src/lib/editor/documents.test.ts, src/app/api/editor/documents/search/route.ts, src/app/api/editor/documents/search/route.test.ts, src/components/editor/GlobalSearchModal.tsx, src/components/editor/GlobalSearchModal.test.tsx, src/components/editor/EditorShell.tsx, src/components/editor/EditorSidebar.tsx

### 기능 — 초안-게시 생명주기 (숨김 ↔ 공개)

- 입력: 게시 여부(on/off)
- 출력·동작: Confluence 페이지 제한(Restriction)을 게시 여부에 맞춰 적용/해제하고, `publishMetadata.isPublished`를 함께 기록한다. 제한 대상은 서비스 계정 자신(직원 개인 계정 매핑 없음). **2026-08-28 갱신(P0-8)**: 예전에는 계정 폴더 내 "초안"/"게시" 두 서브페이지 사이로 문서를 물리적으로 이동시키고 그 위치로 게시 여부를 판단했는데, "Confluence는 아무도 직접 열어보지 않는 DB일 뿐"이라는 결정(P0-7) 이후 폴더 이동이 있던 이유(사람이 트리를 탐색해 구분해본다는 전제) 자체가 사라져 제거했다 — 계정 폴더 하나에 모든 문서가 있고, 게시 여부는 오직 `publishMetadata`와 restriction으로만 판단한다.
- 예외 상황: 제한 적용/해제 API 실패 시 502 + Slack 알림. restriction 변경을 메타데이터 기록보다 항상 먼저 해서, 메타데이터 기록이 실패해도 재시도가 안전하게 수렴한다(restriction 자체가 멱등 연산).

### 기능 — 최상단 계정 관리 페이지(2026-09-03 추가, 2026-09-04 범위 정정)

- **2026-09-04 정정**: 최초 계획 시 "페이지 공유의 공유 대상 검색과 관리자의 계정 상태 확인에 공용으로 쓰인다"고 적었는데, 실제 사용자 의도를 다시 확인한 결과 이는 착오였다 — 사용자가 원래 요청한 것은 "공유할 팀원을 이름·이메일·팀으로 검색해 심플하게 선택만 하는 팝업"이지, 상시 노출되는 계정 조회 화면이 아니었다. 그래서 화면(`/editor/accounts`)과 검색 API는 그대로 두되(향후 재사용을 대비해 폐기하지 않음), 사이드바 등 어떤 메뉴에서도 이 화면으로의 진입 링크를 두지 않는다(연결 고리 끊기) — 화면은 직접 URL로만 접근 가능한 상태로 남는다. - 출력·동작: 계정 목록(이름(이메일), 팀, 접속 허용 뱃지)
- 예외 상황: 검색 API 실패 시 오류 메시지 표시
- 데이터 저장 여부: 예 — data-spec.md의 "AccountIndex" 참고

### Phase 6 — 페이지 공유 (신규, 2026-09-03 계획)

- 핵심 결정(2026-09-03, 사용자와의 대화로 확정): 공유는 소유자와 동일한 편집 권한 하나만 제공(읽기 전용 공유는 범위 밖, 재공유는 소유자만 가능). 동시 편집 충돌은 실시간 잠금/공동편집 없이 기존 버전 충돌 감지(P0-3)에 마지막 수정자 표시만 추가.
- 진행 방식: Phase 5와 동일.

### Phase 7 — 문서 폴더 구조 (신규, 2026-09-07 계획)
- 배경: [SFOOD IT Editor vs Confluence·Notion 비교 리포트](https://claude.ai/code/artifact/5b088947-cb55-4370-8b61-176510385f84)(2026-09-07)에서 가장 뚜렷한 격차로 지적된 항목이다. 현재는 계정 폴더 1개 아래 모든 문서가 형제 노드로 평평하게 쌓이고 다중 태그로만 분류된다 — 태그는 "무엇에 관한 문서인가"를 표현하지만 "이 문서들이 하나의 세트다"는 표현하지 못한다.
- 목표: Confluence·Notion의 폴더 기능을 그대로 흉내 내는 게 목표가 아니다. **사용자가 이 서비스를 계속 쓸 이유를 체감하게 하는 것**이 목표다 — 문서 수가 늘어나도 사이드바가 무너지지 않고, "이 문서들은 하나의 프로젝트/주제에 속한다"는 관계를 표현할 수 있어야 사내 도구로서 매일 쓸 이유가 생긴다. 리포트가 지적한 "태그만으로는 위계·순서·소유 관계를 표현할 수 없다"는 격차를 정확히 겨냥한다.
- 포함 기능: 문서 폴더 구조(생성·이름변경·삭제·이동), 사이드바 폴더 트리 UI, 문서 편집 화면 브레드크럼, 기존 검색·삭제된 문서·공유 문서 기능과의 정합성.
- 핵심 결정:
  - **폴더 데이터 모델: B안(property 기반 가상 폴더 구조)으로 결정** — [Issue #65](https://github.com/sfood-pioneer-1st/sfood-it-editor/issues/65)로 등록(2026-09-07), 2026-09-09 "B안으로 결정" 코멘트로 확정. 계정 폴더의 content property에 폴더 트리(`{id, name, parentId, order}[]`)를 저장하고, 각 문서 property에 `folderId`만 기록한다 — 문서의 실제 Confluence 페이지 위치는 지금처럼 계정 폴더 바로 아래 그대로 둔다(실제 페이지 트리로 옮기는 A안은 기각). 추천안 그대로 채택됐다(이유: P0-8이 이미 "위치=상태 결합은 깨지기 쉽다"는 것을 실제로 겪었고, 폴더는 문서보다 훨씬 자주 만들어지고 이름이 바뀌는 대상이라 그 위험이 더 크다 — 상세는 이슈 본문 참고). **이제 P7-1 착수 가능.**
  - 폴더는 문서당 **최대 1개**만 소속된다(다중 소속 아님) — 태그가 이미 다대다 분류 축을 맡고 있어, 폴더는 그와 겹치지 않는 "위계 하나"를 표현하는 별도 축으로 둔다. 값에 정답이 없는 순수 구조적 가드레일이라 GitHub Issue 없이 직접 정했다(P1-6a와 같은 근거).
  - 폴더 중첩 최대 깊이는 **5단계**로 제한한다 — 무제한 중첩은 사이드바 인덴트가 감당 못 하는 지점이 반드시 오고, 값 자체에 정답이 없는 순수 UX 가드레일이라 GitHub Issue 없이 직접 정했다(P1-6a/P1-6b와 같은 근거).
  - 기존 문서는 전부 **"미분류"(폴더 없음)로 시작**하고, 태그 기반 자동 폴더 추천 같은 것은 하지 않는다 — 오분류 위험을 감수하면서까지 자동화할 이유가 없다는 판단으로, P0-8이 이미 보여준 "추측 대신 명시적 상태" 원칙과 같은 근거다. 사용자가 필요할 때 직접 정리한다.
  - 문서를 폴더 사이로 옮기는 상호작용은 이번 Phase에서 **"이동" 메뉴(대상 폴더 선택 UI) 기반으로 먼저 만든다** — 드래그앤드롭은 이번 범위 밖이다. 드래그앤드롭은 마우스 조작뿐 아니라 키보드 대체 수단까지 함께 갖춰야 이 프로젝트의 접근성 기준(P2-1a~c 선례)을 만족하는데, 계층 구조 자체의 데이터 모델·UI가 실사용으로 검증되지 않은 상태에서 두 가지를 한 번에 다루면 실패 지점이 늘어난다. Phase 3가 Phase 2 완료 직후 UI/UX 진단으로 이어졌던 순서와 같은 방식으로, 이 Phase가 실사용 검증을 마친 뒤 드래그앤드롭을 별도 항목으로 고도화한다.
- 진행 방식: Phase 5·6과 동일 — 항목마다 4파일(task/plan/result/test)을 만들고 개별 PR로 머지·확인 후 다음 항목을 진행한다. 권장 순서: P7-1(완료) → P7-2(완료) → P7-3(완료) → P7-4(완료) → P7-5(완료) → P7-6(완료) → P7-7(완료) → P7-8(완료) → P7-9(완료) → P7-10(완료). **Phase 7 전 항목 완료.**
- 범위 밖(이번 Phase가 다루지 않는 것 — 위 비교 리포트가 함께 지적했지만 이번 요청 범위인 "폴더 구조"가 아니라 향후 별도 Phase 후보로 남긴다): 드래그앤드롭 이동, 즐겨찾기·최근 문서, 문서 템플릿, 인라인 댓글, 버전 되돌리기(rollback), 읽기 전용 공유.

### Phase 8 — 에디터 UI 레이아웃 벤치마킹 (신규, 2026-09-09 계획, Phase 7과 별개 트랙)
- 배경: 사용자가 [support.claude.com/ko](https://support.claude.com/ko)(Anthropic 지원 센터 문서 뷰어)를 지목해 "헤더·좌측 패널·본문 구조가 이 프로젝트와 유사하다"며 픽셀 단위 벤치마킹을 요청했다(2026-09-09). 실제 브라우저로 1440×900(데스크톱 기준) 및 768~1920px 구간을 실측한 결과는 [design.md](./design.md)의 "벤치마킹 — support.claude.com/ko 문서 뷰어 레이아웃 실측 비교 (2026-09-09)" 절에 표로 정리했다 — 아래 각 항목은 그 표를 근거로 한다.
- 목표: 레퍼런스 대비 이 프로젝트의 레이아웃 격차 중 **①이미 유사해 손댈 필요가 없는 것**(사이드바 폭, 본문 최대 폭, 헤더 높이, H1 크기)과 **②실제로 다르고 개선 여지가 있는 것**(사이드바 행 간격/비율, 헤더 검색 진입점, 브레드크럼 시각 스펙, 랜딩 화면 메인 검색, 목차(TOC) 부재)을 구분해, 후자만 손댄다. Phase 7(폴더 트리)과 컴포넌트가 겹칠 수 있는 항목(사이드바)은 있지만, 이 Phase는 Phase 7의 진행 상태와 무관하게 착수 가능하도록 항목을 설계했다(선행 의존성 없음).
- 포함 기능: 헤더 레이아웃 정비, 사이드바 목록 행 간격/비율 재조정, 문서 편집/조회 화면 브레드크럼 시각 스펙(P7-7이 구현할 기능의 스타일 근거), 소개/랜딩 화면 메인 검색 진입점, 문서 보기/편집 화면 우측 목차(TOC) 신규 기능, 본문 최대 폭 미세 조정.
- 핵심 결정:
  - **타이포그래피 스케일(본문/H2/H3 폰트 크기)은 이번 Phase에서 바꾸지 않는다** — 현재 값(16/24/20px)은 2026-08-26에 사내 실제 문서 뷰어 SF-Note를 실측 근거로 확정한 값이라(design.md "문서 편집 화면 — 박스 없는 에디터 캔버스 구조" 절 참고), 성격이 다른 일반 헬프센터 하나만 근거로 되돌리지 않는다. P8-7은 레퍼런스와의 비교표를 design.md에 남기는 것까지만 하고 구현하지 않는다 — 축소를 원하면 별도 GitHub Issue로 결정한 뒤 진행한다.
  - **TOC 활성 항목 색상은 레퍼런스(무채색 검정 바)를 그대로 베끼지 않고 이 프로젝트의 브랜드색 관례(`--color-brand`, `.sidebar-row-active`와 동일한 원칙)를 따른다** — CLAUDE.md "커스텀 색상 하드코딩 금지" 원칙 및 design.md의 WCAG AA 대비 규칙 적용.
  - **헤더 높이(56px, `h-14`)는 레퍼런스(60px)와 4px 차이가 있으나 변경하지 않는다** — 기존에 "두 헤더가 나란히 있을 때 라인이 어긋나 보인 사례"를 근거로 고정한 값이라(design.md "영역별 기준 — 헤더" 절), 4px 차이만으로 뒤집을 근거가 아니다.
  - **본문 최대 폭은 820px→830px로만 맞춘다(P8-6)** — 레퍼런스 실측값과 10px 차이라 판단 근거가 필요 없는 사소한 조정이라 GitHub Issue 없이 직접 정했다(P1-6a와 같은 근거).
  - **랜딩 화면 메인 검색(P8-4)은 새 검색 로직이 아니다** — 레퍼런스 실측 결과 히어로의 큰 검색창도 실제로는 기존 헤더 검색 버튼과 동일한 모달을 여는 트리거 버튼이었다(design.md "8. 검색" 절 참고). 이 프로젝트도 기존 `GlobalSearchModal`(Ctrl+K)을 그대로 열게만 하고, 검색 API·로직은 손대지 않는다.
- 진행 방식: 항목마다 4파일(task/plan/result/test)을 만들고 개별 PR로 머지·확인 후 다음 항목을 진행한다(Phase 5·6·7과 동일). 항목 간 선행 의존성은 없어 순서 상관없이 진행 가능하나, 권장 순서는 P8-1 → P8-4 → P8-6(가벼운 항목부터) → P8-3 → P8-2 → P8-5(TOC, 신규 컴포넌트라 가장 크다) → P8-7(구현 없는 비교표만).
- 범위 밖: 헤더 높이 변경, 타이포그래피 스케일 변경(P8-7은 비교만), 사이드바/본문 폭의 큰 구조 변경(이미 유사해 불필요), "LLM용 복사" 버튼 등 레퍼런스의 콘텐츠 기능(이 프로젝트 문서 작성 도구의 목적과 무관).
