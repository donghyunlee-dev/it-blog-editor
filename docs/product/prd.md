## 🛠️ 개발 스펙 정의
- 기술 스택·인증·데이터 저장·배포 방향의 상세 근거는 [architecture.md](./architecture.md)를 참고한다. 요약:
  - Next.js 16(App Router) + React 19 + TypeScript, AWS 배포, 별도 스테이징 없음
  - 인증: next-auth(Auth.js) v5 + AX Auth(사내 SSO) Credentials 프로바이더
  - 저장소: 자체 DB 없음, Confluence Cloud REST API(v2 우선, 일부 v1)가 유일한 저장소
  - 알림: Slack Incoming Webhook(운영 이상 감지)
- 코드 구조 원칙: `src/lib/confluence/client.ts`(Confluence REST 저수준 래퍼) → `src/lib/editor/*.ts`(도메인 로직) → `src/app/api/editor/**/route.ts`(얇은 API 컨트롤러) → `src/app/editor/**/page.tsx` + `src/components/editor/*.tsx`(화면). 도메인 계층은 `ValidationError`/`NotFoundError`/`ConflictError`/`UnauthorizedError`를 던지고, `src/lib/api-response.ts`의 `toErrorResponse()`가 공통 에러 응답으로 변환한다.
- 에디터/UI 라이브러리: TipTap(WYSIWYG 엔진, 문서 원본은 JSON으로 저장), `@sfood/ui` + Tailwind CSS(사내 디자인 시스템 — [design.md](./design.md) 참고). 이미지는 `confluence-attachment://{filename}` 스킴으로 Confluence storage format의 `<ac:image>`에 매핑한다(변환기는 자체 작성, `marked`는 더 이상 쓰지 않음).
- 실제 Confluence 쓰기는 항상 공용 서비스 계정으로만 이루어진다. 로그인한 직원의 이메일은 Confluence 신원이 아니라 content property로만 기록되는 "실제 작성자 식별자"다.

## 🧩 기능별 정의

### 기능 — 로그인 (AX Auth)
- 설명: 사내 MS 계정으로 로그인한다. AX Auth가 SSO를 대행한다.
- 입력: 없음(리다이렉트 방식 — AX Auth 로그인 페이지에서 인증 후 콜백으로 loginToken 전달)
- 출력·동작: `/api/auth/ax-callback`이 loginToken을 검증하고 next-auth 세션(이메일)을 생성, `/editor`로 이동
- 예외 상황: 토큰 누락·검증 실패 시 `/login?error=...`로 리다이렉트
- 데이터 저장 여부: 아니오 (세션은 next-auth가 관리, 별도 저장 없음)
- API 필요 여부: 예 — api-spec.md의 인증 관련 엔드포인트 참고
- 상태: 완료(기존 구현)

### 기능 — 내 문서함 조회
- 설명: 로그인한 사용자의 계정 폴더 하위 "초안"+"게시" 문서를 함께 보여주고 상태 뱃지로 구분한다. 계정 폴더(및 초안/게시 서브페이지)가 없으면 자동 생성한다. 게시해도 목록에서 사라지지 않는다.
- 입력: 세션 이메일
- 출력·동작: 문서 목록(제목, 최종 수정일, 게시 여부)
- 예외 상황: Confluence 연동 실패 시 502 + Slack 알림
- 데이터 저장 여부: 예 — data-spec.md의 "계정 폴더"/"문서" 참고
- API 필요 여부: 예 — `GET /api/editor/folder`, `GET /api/editor/documents`
- 상태: 완료 — 산출물: src/lib/editor/folder.ts, src/lib/editor/folder.test.ts, src/lib/editor/documents.ts, src/lib/editor/documents.test.ts, src/app/api/editor/folder/route.ts, src/app/api/editor/documents/route.ts, src/app/editor/layout.tsx, src/lib/editor/tag-suggestions.ts

### 기능 — 문서 전체 검색(Ctrl+K)
- 설명: 사이드바의 상시 검색(제목·태그, 클라이언트 필터)과 별개로, `Ctrl+K`/`Cmd+K`로 여는 전역 팝업에서 제목·태그·본문(TipTap 문서에서 추출한 순수 텍스트)을 함께 검색한다([Issue #7](https://github.com/sfood-pioneer-1st/sfood-it-editor/issues/7), P1-1a 후속, 2026-09-03 결정·구현). `/editor/*` 어느 화면에서든 열 수 있다. Notion의 Ctrl+K 검색 화면을 참고해 좌측 결과 목록 + 우측 미리보기의 2단 레이아웃으로 재구성했다(2026-09-03 재구성).
- 입력: 검색어(자유 텍스트, 300ms 디바운스 후 서버에 전송), "제목만" 필터 토글(클라이언트에서 결과를 다시 거름, 재조회 없음)
- 출력·동작: 일치하는 문서를 최종 수정일 기준 오늘/어제/최근 7일/이전 구간으로 묶어 좌측 목록에 표시(각 행: 상태 아이콘 + 제목 + 태그). 방향키로 강조를 옮기면 우측 패널에 그 문서의 태그·제목·본문 스니펫 미리보기가 나타난다. 클릭하거나 Enter를 누르면 해당 문서 편집 화면으로 이동
- 예외 상황: 검색 API 실패 시 오류 메시지 표시. 개인 폴더가 없으면 빈 목록. 결과가 없으면 안내 문구
- 데이터 저장 여부: 아니오(조회 전용)
- API 필요 여부: 예 — `GET /api/editor/documents/search?q=...`(사용자가 팝업을 열고 입력할 때만 호출되는 온디맨드 API — 사이드바가 매 렌더링마다 쓰는 `listDocuments()`와는 별개). 응답에 미리보기용 `snippet`(본문 중 검색어 주변 문맥, 없으면 본문 앞부분) 필드 포함

### 기능 — 초안-게시 생명주기 (숨김 ↔ 공개)

- 예외 상황: 제한 적용/해제 API 실패 시 502 + Slack 알림. restriction 변경을 메타데이터 기록보다 항상 먼저 해서, 메타데이터 기록이 실패해도 재시도가 안전하게 수렴한다(restriction 자체가 멱등 연산).

### 기능 — 문서 태그 지정

  매칭되는 가벼운 키워드"로 용도를 좁힌다 — 이름 변경/병합 같은 관리 기능이 없고 자동완성도
  작성자 본인 문서로만 한정되어, 정교한 분류 체계로 쓰기엔 관리 기능이 부실하다고 판단했다. 이에

  매칭)으로 흡수했다(P12-1, 별도 PR). (2) 편집 화면의 태그 입력 영역은 제목 바로 아래(2줄 차지)

  포함하고 있어 별도 변경이 필요 없었다. 태그 이름 변경/병합 기능은 이 좁아진 용도 하에서는

### 기능 — 최상단 계정 관리 페이지(2026-09-03 추가, 2026-09-04 범위 정정)

- **2026-09-04 정정**: 최초 계획 시 "페이지 공유의 공유 대상 검색과 관리자의 계정 상태 확인에 공용으로 쓰인다"고 적었는데, 실제 사용자 의도를 다시 확인한 결과 이는 착오였다 — 사용자가 원래 요청한 것은 "공유할 팀원을 이름·이메일·팀으로 검색해 심플하게 선택만 하는 팝업"이지, 상시 노출되는 계정 조회 화면이 아니었다. 그래서 화면(`/editor/accounts`)과 검색 API는 그대로 두되(향후 재사용을 대비해 폐기하지 않음), 사이드바 등 어떤 메뉴에서도 이 화면으로의 진입 링크를 두지 않는다(연결 고리 끊기) — 화면은 직접 URL로만 접근 가능한 상태로 남는다. - 출력·동작: 계정 목록(이름(이메일), 팀, 접속 허용 뱃지)
- 예외 상황: 검색 API 실패 시 오류 메시지 표시
- 데이터 저장 여부: 예 — data-spec.md의 "AccountIndex" 참고

### Phase 7 — 문서 폴더 구조 (신규, 2026-09-07 계획)
- 배경: [SFOOD IT Editor vs Confluence·Notion 비교 리포트](https://claude.ai/code/artifact/5b088947-cb55-4370-8b61-176510385f84)(2026-09-07)에서 가장 뚜렷한 격차로 지적된 항목이다. 현재는 계정 폴더 1개 아래 모든 문서가 형제 노드로 평평하게 쌓이고 다중 태그로만 분류된다 — 태그는 "무엇에 관한 문서인가"를 표현하지만 "이 문서들이 하나의 세트다"는 표현하지 못한다.
- 목표: Confluence·Notion의 폴더 기능을 그대로 흉내 내는 게 목표가 아니다. **사용자가 이 서비스를 계속 쓸 이유를 체감하게 하는 것**이 목표다 — 문서 수가 늘어나도 사이드바가 무너지지 않고, "이 문서들은 하나의 프로젝트/주제에 속한다"는 관계를 표현할 수 있어야 사내 도구로서 매일 쓸 이유가 생긴다. 리포트가 지적한 "태그만으로는 위계·순서·소유 관계를 표현할 수 없다"는 격차를 정확히 겨냥한다.
- 포함 기능: 문서 폴더 구조(생성·이름변경·삭제·이동), 사이드바 폴더 트리 UI, 문서 편집 화면 브레드크럼, 기존 검색·삭제된 문서·공유 문서 기능과의 정합성.
- 핵심 결정:
  - **폴더 데이터 모델: B안(property 기반 가상 폴더 구조)으로 결정** — [Issue #65](https://github.com/sfood-pioneer-1st/sfood-it-editor/issues/65)로 등록(2026-09-07), 2026-09-09 "B안으로 결정" 코멘트로 확정. 계정 폴더의 content property에 폴더 트리(`{id, name, parentId, order}[]`)를 저장하고, 각 문서 property에 `folderId`만 기록한다 — 문서의 실제 Confluence 페이지 위치는 지금처럼 계정 폴더 바로 아래 그대로 둔다(실제 페이지 트리로 옮기는 A안은 기각). 추천안 그대로 채택됐다(이유: P0-8이 이미 "위치=상태 결합은 깨지기 쉽다"는 것을 실제로 겪었고, 폴더는 문서보다 훨씬 자주 만들어지고 이름이 바뀌는 대상이라 그 위험이 더 크다 — 상세는 이슈 본문 참고). **이제 P7-1 착수 가능.**
  - 폴더는 문서당 **최대 1개**만 소속된다(다중 소속 아님) — 태그가 이미 다대다 분류 축을 맡고 있어, 폴더는 그와 겹치지 않는 "위계 하나"를 표현하는 별도 축으로 둔다. 값에 정답이 없는 순수 구조적 가드레일이라 GitHub Issue 없이 직접 정했다(P1-6a와 같은 근거).
  - 폴더 중첩 최대 깊이는 **5단계**로 제한한다 — 무제한 중첩은 사이드바 인덴트가 감당 못 하는 지점이 반드시 오고, 값 자체에 정답이 없는 순수 UX 가드레일이라 GitHub Issue 없이 직접 정했다(P1-6a/P1-6b와 같은 근거).
  - 기존 문서는 전부 **"미분류"(폴더 없음)로 시작**하고, 태그 기반 자동 폴더 추천 같은 것은 하지 않는다 — 오분류 위험을 감수하면서까지 자동화할 이유가 없다는 판단으로, P0-8이 이미 보여준 "추측 대신 명시적 상태" 원칙과 같은 근거다. 사용자가 필요할 때 직접 정리한다.
  - 문서를 폴더 사이로 옮기는 상호작용은 이번 Phase에서 **"이동" 메뉴(대상 폴더 선택 UI) 기반으로 먼저 만든다** — 드래그앤드롭은 이번 범위 밖이다. 드래그앤드롭은 마우스 조작뿐 아니라 키보드 대체 수단까지 함께 갖춰야 이 프로젝트의 접근성 기준(P2-1a~c 선례)을 만족하는데, 계층 구조 자체의 데이터 모델·UI가 실사용으로 검증되지 않은 상태에서 두 가지를 한 번에 다루면 실패 지점이 늘어난다. Phase 3가 Phase 2 완료 직후 UI/UX 진단으로 이어졌던 순서와 같은 방식으로, 이 Phase가 실사용 검증을 마친 뒤 드래그앤드롭을 별도 항목으로 고도화한다.
- 진행 방식: Phase 5·6과 동일 — 항목마다 4파일(task/plan/result/test)을 만들고 개별 PR로 머지·확인 후 다음 항목을 진행한다. 권장 순서: P7-1(완료) → P7-2(완료) → P7-3(완료) → P7-4(완료) → P7-5(완료) → P7-6(완료) → P7-7(완료) → P7-8(완료) → P7-9(완료) → P7-10(완료). **Phase 7 전 항목 완료.**
- 범위 밖(이번 Phase가 다루지 않는 것 — 위 비교 리포트가 함께 지적했지만 이번 요청 범위인 "폴더 구조"가 아니라 향후 별도 Phase 후보로 남긴다): 드래그앤드롭 이동, 즐겨찾기·최근 문서, 문서 템플릿, 인라인 댓글, 버전 되돌리기(rollback), 읽기 전용 공유.

### Phase 8 — 에디터 UI 레이아웃 벤치마킹 (신규, 2026-09-09 계획, Phase 7과 별개 트랙)

- 진행 방식: 항목마다 4파일(task/plan/result/test)을 만들고 개별 PR로 머지·확인 후 다음 항목을 진행한다(Phase 5·6·7과 동일). 항목 간 선행 의존성은 없어 순서 상관없이 진행 가능하나, 권장 순서는 P8-1 → P8-4 → P8-6(가벼운 항목부터) → P8-3 → P8-2 → P8-5(TOC, 신규 컴포넌트라 가장 크다) → P8-7(구현 없는 비교표만).

### Phase 9 — 콜아웃(패널) 아이콘 커스터마이징 (신규, 2026-09-11 계획)
- 배경: [노션 페이지(SFOOD 생성형 AI 업무 지침 가이드) 재현 검토](https://bird-earl-256.notion.site/SFOOD-AI-3d7be4fbb834817f8ed2c4742219ce7b)에서, 원본이 콜아웃마다 다른 이모지(📷/💡/⚠️ 등)를 자유롭게 쓰는 반면 이 프로젝트의 패널(`panel` 노드, `src/components/editor/RichTextEditor.tsx`)은 정보/경고/노트 3종 고정이고 애초에 아이콘 자체가 구현돼 있지 않다는 격차가 드러났다(조사 결과: 렌더링은 CSS 클래스의 테두리·배경색뿐, 아이콘 요소가 없음). 사용자가 이 격차를 좁히는 기능 추가를 요청했다(2026-09-11).
- 목표: 콜아웃 아이콘을 큐레이션된 이모지 목록 중에서 자유롭게 고를 수 있게 하고, 데이터 모델을 노션의 콜아웃 블록 스키마(`icon: {type:"emoji", emoji}`, `color`)와 최대한 1:1로 맞춰 **노션 데이터와 실제 상호 호환**되게 설계한다(사용자 확인, 2026-09-11) — 단, 노션 문서를 실제로 가져오거나 내보내는 가져오기/내보내기 파이프라인 자체는 이번 Phase가 만들지 않는다(아래 "범위 밖" 참고). 이번 Phase는 "그 기능이 나중에 생겼을 때 이 컴포넌트의 데이터 모델을 다시 설계하지 않아도 되는 것"까지가 목표다.
- 포함 기능: 패널 노드에 `icon` attrs 추가(노션 호환 스키마 설계 포함), Confluence storage 직렬화에 아이콘 보존, 슬래시 메뉴로 삽입한 패널의 타입별 기본 아이콘, 콜아웃 블록에 아이콘 선택 UI(큐레이션된 이모지 그리드) 추가.
- 핵심 결정(2026-09-11, 사용자와의 대화로 확정):
  - "노션과 호환"의 의미는 시각적 재현이 아니라 **노션 데이터와의 실제 상호 호환**(향후 가져오기/내보내기가 이 데이터 모델을 그대로 재사용할 수 있는 수준)이다.
  - 아이콘 선택 UI는 전체 유니코드 이모지 피커가 아니라 **큐레이션된 목록 중에서 고르는 방식**이다 — 목록 자체는 [Issue #101](https://github.com/sfood-pioneer-1st/sfood-it-editor/issues/101)로 등록해 답을 받은 뒤 확정한다. **P9-2(아이콘 선택 UI)는 이 이슈 답변 전까지 착수하지 않는다.**
  - 기존 3종 색상 테마(정보/경고/노트)는 그대로 유지한다 — 이번 요청은 "아이콘"에 관한 것이고 색상 팔레트 확장(노션처럼 배경색 자유 선택)은 요청 범위 밖이라 임의로 넓히지 않는다.
  - 기존 문서(아이콘 attrs가 없는 패널)는 타입별 고정 기본 아이콘(정보=ℹ️/경고=⚠️/노트=📝)으로 보정한다 — 마이그레이션 스크립트 없이 조회 시점 기본값으로 처리(P5-1의 `accountMeta` 보정과 같은 패턴).
- 진행 방식: Phase 5·6·7·8과 동일 — 항목마다 4파일(task/plan/result/test)을 만들고 개별 PR로 머지·확인 후 다음 항목을 진행한다. P9-1(데이터 모델·storage) → P9-2(아이콘 선택 UI, Issue #101 답변 후 착수) 순서를 권장한다.

### Phase 10 — 문서 링크 카드 블록 (신규, 2026-09-11 계획)
- 배경: [노션 페이지 재현 검토](https://bird-earl-256.notion.site/SFOOD-AI-3d7be4fbb834817f8ed2c4742219ce7b)에서 지적된 두 번째 격차 — 노션은 다른 페이지를 아이콘+제목+화살표가 있는 카드형 블록으로 삽입해 클릭 한 번으로 이동할 수 있는데, 이 프로젝트는 일반 텍스트 하이퍼링크만 있고 이런 카드형 블록이 없다. 사용자가 Phase 9(콜아웃 아이콘) 완료 후 이어서 요청했다(2026-09-11).
- 목표: 에디터 안에서 이 서비스의 다른 문서를 검색해 아이콘+제목이 있는 카드로 삽입하고, 클릭하면 그 문서로 이동하는 `documentLink` 블록을 추가한다.
- 포함 기능: `documentLink` TipTap 노드(카드 NodeView, 클릭 시 `/editor/{pageId}`로 이동), 슬래시 메뉴 "문서 링크" 항목, 문서 검색 피커 모달(기존 `GET /api/editor/documents/search` 재사용), Confluence storage 직렬화(사람이 읽을 수 있는 텍스트로 — 기존 `panel`과 같은 이유로 역방향 파싱은 하지 않음).
- 핵심 결정(2026-09-11, GitHub Issue 없이 직접 정함 — 값 자체에 정답이 없는 구조적 선택이라 P1-6a와 같은 근거로 바로 진행):
  - **제목은 삽입 시점 스냅샷을 캐시해 보여준다**(노션처럼 항상 최신 제목을 실시간 조회하지 않음) — 카드 하나당 렌더링마다 대상 문서를 다시 조회하면 카드가 많은 문서에서 API 호출이 N배로 늘어난다. 원본 문서 제목이 바뀌면 카드는 갱신되지 않으니(알려진 제약), 최신 제목을 반영하려면 카드를 지우고 다시 삽입해야 한다.
  - **링크 대상은 검색 피커로 고른 문서로 한정한다**(pageId를 직접 입력하는 방법은 없음) — 기존 문서 검색 API(`searchDocuments`)가 이미 "내 계정 폴더 문서만" 범위로 좁혀져 있어, 자연스럽게 타인의 비공개 문서를 링크할 수 없다.
  - **공유받은 문서(내 소유가 아닌 문서)는 이번 피커의 검색 대상에 포함하지 않는다** — `searchDocuments`가 계정 폴더 기준이라 기본적으로 내 문서만 나온다. 필요해지면 별도 항목으로 확장한다.
  - **아이콘은 모든 카드에 동일한 고정 이모지(📄)를 쓴다** — 문서 자체에 아이콘 필드가 없어(조사 결과), 문서마다 다른 아이콘을 지원하려면 문서 데이터 모델 확장이 먼저 필요한 별개의 큰 작업이다. 이번 범위는 카드 블록 자체이지 문서 아이콘 기능이 아니다.
  - 새로 저장하지 않은 문서(`pageId` 없음)에서는 "문서 링크" 슬래시 항목 자체를 노출하지 않는다 — 기존 "이미지" 슬래시 항목과 같은 제약(`RichTextEditor.tsx`의 `pageId ? ... : ...` 분기)을 그대로 재사용한다.
- 진행 방식: Phase 5~9와 동일 — task/plan/result/test 4파일 + 개별 PR.
- 범위 밖: 실시간 제목 갱신, pageId 직접 입력, 공유받은 문서 링크, 문서별 커스텀 아이콘, 카드 미리보기(본문 스니펫 등 — 노션의 "미리보기" 모드는 다루지 않는다).

### Phase 13 — 사이드바 문서함 행 밀도·들여쓰기 조정 (신규, 2026-09-14 계획)
- 배경: 사용자가 폴더 2~3개·문서 10개 미만으로 실사용 테스트를 하던 중(캡처로 확인) "문서가
  10개도 안 되는데 리스트 영역의 2/3이 찬다"고 지적했다. 실측 결과 폴더 행·문서 행 모두
  `py-2`(P8-2에서 올린 값)를 쓰고 있어 한 행이 36px를 차지했고, 검색창·새 문서 버튼·`nav`
  패딩·폴더 라벨 여백이 트리 진입 전에 겹겹이 쌓여 있었다. "폴더와 페이지 사이 간격도 넓고
  폴더 안의 페이지 리스트라는 느낌이 안 난다"는 지적도 있었는데, 행 사이 간격(`gap-0.5`, 2px)은

  선택 상태 배경색(핑크, `.sidebar-row-active`)이 위아래로 넓어 보인다는 지적도 행 padding에

  버튼·`nav`·폴더 라벨)의 padding/margin을 줄인다. 폴더 하위 목록에 세로 가이드라인을 추가하는

  제약으로 시각적 미세조정을 검증할 방법이 없어, 사용자가 이번 변경을 확인한 뒤 필요하면 별도

- 범위 밖: 폴더 하위 목록 세로 가이드라인(위 참고), 사이드바 태그 필터·태그 입력 위치(Phase

  지적했다 — (1) "선택한 페이지 영역의 왼쪽은 여백이 없어. 게시 아이콘하고 붙어 있어" — 문서

  파일의 선택 영역이 표시되어야 하는데 없어" — 확인 결과 라이트 모드에서

  이미 겪은 문제) `hover:bg-surface-raised`가 무효했다. 문서 행에 `pl-2`(폴더 행은 `pl-1`)를

  명시적으로 요청한 것은 아니라 이번 범위에는 포함하지 않았다.

### Phase 14 — 사이드바 문서 행 컨텍스트 메뉴 전환 (신규, 2026-09-14 계획)
- 배경: 사이드바 문서 행마다 "다른 폴더로 이동" 아이콘이 상시(호버 시) 노출되는데, 사용자가
  Notion·Confluence·Google Drive 등을 비교한 뒤 "기능이 늘어날 때마다 헤더나 행에 아이콘을
  새로 추가하지 말고, `⋯`(더보기) 하나로 모아 컨텍스트 메뉴에서 확장하자"고 결정했다. 확인
  결과 `@sfood/ui`에 정확히 이 용도의 `DropdownMenu`(`trigger` + `DropdownItem[]`,
  `label`/`onClick`/`icon`/`danger`/`divider` 지원)가 이미 있고, 같은 패키지의
  `FileExplorer.itemActions`도 동일 패턴("항목별 우측 액션 메뉴")을 이미 쓰고 있어 새로
  만들지 않고 그대로 재사용한다.
- 핵심 결정(2026-09-14, 사용자와의 대화로 확정): 이번 범위는 **사이드바 "내 문서" 목록의
  문서 행만**이다. 사용자가 명시적으로 범위를 좁혔다 — 에디터 헤더의 "삭제"·"이력" 버튼은
  이번엔 건드리지 않고("헤더에 ⋯을 추가하는 건 안 해도 돼"), 폴더 행의 액션 아이콘(하위
  폴더 추가/이름변경/삭제)도 "폴더가 아직 많지 않다"는 이유로 보류한다. 문서 행의 기존
  "다른 폴더로 이동" 단일 버튼을 `⋯` 트리거 + `DropdownMenu`(현재 항목 1개)로 교체한다 —
  향후 기능이 늘어나면 이 메뉴에 항목만 추가하는 구조로 만든다.
- 진행 방식: Phase 5~13과 동일 — task/plan/result/test 4파일 + 개별 PR.
- 범위 밖: 에디터 헤더 컨텍스트 메뉴화(향후 헤더 버튼을 실제로 제거하게 되면 남는 버튼들의
  정렬을 다시 조정해야 한다는 점을 사용자가 미리 언급함), 폴더 행 액션 아이콘 통합, 메뉴
  항목 추가(지금은 "다른 폴더로 이동" 1개만).
- P14-1 적용 후속(2026-09-14, 같은 대화·같은 PR — P14-2): 위 "헤더에 ⋯을 추가하는 건 안 해도
  돼"를 "헤더는 그대로 두라"는 뜻으로 잘못 이해했었다 — 사용자가 정정: 실제로는 (1) 에디터
  헤더에 **별도의** 옵션 메뉴를 새로 만들지 말라는 뜻이었고, (2) 헤더의 "이력"·"삭제" 버튼은
  **제거**하고 그 기능을 사이드바 문서 옵션(⋯) 메뉴에 **항목으로 추가**해 "이동·이력·삭제"
  3개를 한 메뉴로 모으는 것이 목표였다. 추가로 메뉴가 트리거 기준 왼쪽으로 펼쳐져 문서
  제목과 겹치는 문제도 지적받아, `@sfood/ui`의 `DropdownMenu`가 위치를 바꾸는 props를 제공하지
  않으므로 CSS로 `[role="menu"]`만 오른쪽(본문/페이지 방향)으로 덮어썼다.
- P14-2 적용 후속(2026-09-14, 같은 대화·같은 PR — P14-3): CSS로 방향만 바꿔도 메뉴가 "문서함
  패널 안으로 들어가서 보이지 않는" 문제가 남아 있었다(사용자 지적 — "z-index를 완전히
  밖으로 빼야 할 거 같아"). 코드로 원인을 확인한 결과, 사이드바 문서 목록을 감싸는 `<nav
  overflow-y-auto>`가 CSS 스펙상(overflow-y가 visible이 아니면 overflow-x도 auto로 강제
  계산됨) 가로로 넘치는 자손도 클리핑하고 있었다 — `DropdownMenu`의 팝업이 그 안에 있어
  사이드바 폭을 넘는 순간 잘렸다. z-index는 스태킹 순서만 바꿀 뿐 overflow 클리핑을 뚫지
  못해 사용자의 제안과는 다른 해법이 필요했다: `DropdownMenu` 사용을 그만두고, 팝업을
  `<nav>` 바깥 형제 위치에 `position: fixed` + 트리거의 `getBoundingClientRect()` 좌표로
  직접 그리는 커스텀 구현으로 교체했다(접근성 역할은 동일하게 유지).

### Phase 16 — "삭제된 문서" Modal → 전용 페이지 전환 (신규, 2026-09-14 계획)
- 배경: "삭제된 문서"(P1-2b)는 사이드바 버튼이 여는 `Modal`이었는데, 사용자 지적 — "삭제된
  문서는 늘어날 수록 팝업으로 감당이 안돼. 삭제된 문서 클릭 시 오른쪽 페이지 영역에 상단
  검색과 하단 삭제된 페이지 리스트가 나오도록 구성을 해야 할 것 같아. 검색해서 복구할 수
  있으면 좋을 것 같고, 삭제된 페이지 정보 표시도 좀 더 상세하게 보여 줄 수 있을 것 같아."
- 핵심 결정: (1) Modal 대신 `/editor/trash` 전용 페이지(다른 `/editor/*` 화면과 같은 서버
  컴포넌트가 데이터를 미리 조회하는 패턴). (2) 상단 검색(제목·태그, 사이드바 검색과 동일
  로직) + 하단 목록. (3) 목록 행에 게시 상태·태그·원래 폴더를 추가로 보여주기 위해
  `DeletedDocumentEntry`(레지스트리 저장 항목)에 삭제 시점 스냅샷(`tags`/`isPublished`/
  `folderId`)을 추가하고, `deleteDocument()`가 페이지가 실제로 삭제되기 직전에 이 값을
  함께 기록한다. 폴더는 id만 저장하고 이름은 조회 시점에 현재 폴더 트리에서 다시 찾는다
  (이름 변경에 안전하게).
- 진행 방식: Phase 5~14와 동일 — task/plan/result/test 4파일 + 개별 PR.
- 범위 밖: 삭제된 문서 미리보기(본문 확인), 완전 삭제(영구 삭제) 버튼.

### Phase 17 — 편집 컨텍스트 메뉴 결함·부족 기능 정비 (신규, 2026-09-15 계획)
- 배경: 사용자가 실사용 중 편집 화면에서 뜨는 메뉴 6가지 문제를 지적했다 — (1) 이미지 삽입이
  안 됨(아무 반응 없음), (2) 문서 링크 삽입이 안 됨, (3) 표 툴바의 행 삭제·열 삭제·표 전체
  삭제 아이콘 3개가 전부 같은 휴지통 모양이라 구분이 안 됨, (4) 인라인 코드와 코드 블록의
  차이를 시각적으로 구분 못함, (5) 코드 블록 편집이 불편함(Tab 들여쓰기 안 됨, 언어 선택 없음,
  코드 복사 버튼 없음), (6) 메뉴 항목에 아이콘이 없어 텍스트만 나열됨. 코드 조사 결과 이
  프로젝트에는 브라우저 우클릭(contextmenu) 기반 메뉴가 존재하지 않고, 사용자가 말한
  "컨텍스트 메뉴"는 `/` 슬래시 메뉴(`SlashCommandExtension.ts`)와 표 선택 시 뜨는 버블 툴바
  (`RichTextEditor.tsx`의 `TableToolbar`)를 가리킨다.
- 원인 조사 결과:
  - (1)(2) `RichTextEditor.tsx`가 신규 문서(저장 전, `pageId` 미확정) 상태에서는 슬래시 메뉴의
    "이미지"·"문서 링크" 항목 자체를 목록에서 빼버린다 — `/`를 쳐도 항목이 안 보이거나 "일치
    하는 항목 없음"만 떠서 "아무 반응 없음"으로 느껴진다. 같은 상황에서 드래그앤드롭/붙여넣기
    업로드 경로는 토스트로 안내하는데 슬래시 메뉴만 조용히 숨기는 비대칭이 원인이다.
  - (3) 행 삭제·열 삭제·표 전체 삭제 버튼이 동일한 `TrashIcon` 컴포넌트를 재사용한다.
    `Tooltip`/`aria-label`로 텍스트 구분은 있으나 아이콘 모양 자체가 같아 마우스를 올리거나
    스크린리더를 쓰지 않으면 구분이 안 된다.
  - (4) 인라인 코드·코드 블록 모두 `@tailwindcss/typography` 기본 `.prose` 스타일만 쓰고 별도
    강조 클래스가 없다. 인라인 코드 색이 본문(`--color-foreground`)과 거의 같아 배경 강조 없이는
    구분이 어렵다.
  - (5) `CodeBlockLowlight.configure({ lowlight })`에서 `enableTabIndentation` 옵션이 꺼져
    있어(기본값 false) Tab 키가 무시되고 포커스가 에디터 밖으로 빠진다. 언어 선택 UI는 애초에
    "문법 강조 자동 추정까지"로 범위를 좁혀 의도적으로 만들지 않았다(주석에 명시, lowlight
    `common` 번들이 이미 자주 쓰는 언어를 폭넓게 포함해 `lowlight.listLanguages()`로 목록을 바로
    쓸 수 있다). 복사 버튼은 코드 블록에 커스텀 노드뷰가 없어 얹을 자리 자체가 없다.
  - (6) 슬래시 메뉴의 `CommandItem` 인터페이스가 `{ title, run }`뿐이라 아이콘 필드가 없고,
    렌더러도 텍스트만 그린다.
- 추가로 발견한 문제(사용자가 지적하지 않았지만 조사 중 확인):
  - 표 툴바에서 행 삭제·열 삭제는 확인 없이 즉시 실행되는데 표 전체 삭제만 `Modal` 확인을
    거친다 — 파괴성 기준이 일관되지 않다.
  - 이미지 노드 자체에는 alt 텍스트 입력만 있고, 삭제나 다시 업로드를 위한 버튼이 없다.
- 핵심 결정: 항목을 독립적으로 진행 가능한 단위로 쪼갠다(아래 체크리스트). (5)는 Tab
  들여쓰기·언어 선택·복사 버튼을 P17-5a/b/c 3개로 분리한다 — 각각 에디터 옵션 설정/신규
  노드뷰 UI 작성/클립보드 연동으로 변경 영역이 달라 하나로 묶으면 리뷰 단위가 커진다.
- 범위 밖: 브라우저 우클릭 기반 컨텍스트 메뉴 신설(현재 슬래시 메뉴·버블 툴바 패턴이 기존
  설계와 일관적이라고 판단 — 사용자가 실제 우클릭 메뉴를 원하면 별도 요청 필요), lowlight
  `common` 번들 밖 언어 추가.
- 진행 방식: Phase 5~16과 동일 — 항목마다 4파일(task/plan/result/test)을 만들고 개별 PR로
  머지·확인 후 다음 항목을 진행한다. 사용자가 직접 지적한 P17-1~P17-6을 먼저 진행하고, 조사 중

  상황의 안내 방식(토스트만으로 충분한지, 임시 자동 저장 후 진행할지 등)이 아직 정해지지
