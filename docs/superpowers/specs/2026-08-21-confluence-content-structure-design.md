# Confluence 콘텐츠 구조 설계

- 날짜: 2026-08-21 (개정: 2026-08-24 — 루트 분리 구조 → 계정 폴더 내부 구조로 변경)

## 개정 이력 (2026-08-24)

착수 전(코드 반영 전) 단계에서 구조를 재검토했다. 원래는 "Space 홈페이지 → 초안 루트/게시됨 루트" 두 루트를 먼저 나누고 그 밑에 계정별 폴더를 두는 구조였는데, 이를 "Space 홈페이지 → 계정(이메일) 폴더 → 그 안에서 초안/게시 구분"으로 뒤집었다. 아래 "채택한 설계"는 이 개정된 구조를 반영한 최종본이며, 이전 버전(루트 분리 방식)은 "검토한 접근법" 절에 접근법 B의 역사적 맥락으로만 남겨둔다.

바뀐 이유와 트레이드오프:
- 계정 폴더 하위에 초안/게시 서브폴더를 두면, 관리자가 최초 1회 "초안"/"게시됨" 루트 페이지를 수동으로 만들고 Restriction을 설정하는 운영 작업이 완전히 사라진다 — 계정 폴더 생성 시 코드가 서브폴더 두 개를 함께 만들면 된다.
- **트레이드오프 1**: 계정 폴더(이메일이 제목) 자체는 제한을 걸지 않고 공개한다 — 다른 직원이 "이 사람이 이 서비스를 쓰고 있다"는 사실(이메일)을 알 수 있게 된다. 초안 "내용"은 여전히 숨겨지므로 핵심 보안 요건은 유지된다. (검토됨·수용)
- **트레이드오프 2**: 게시된 문서가 작성자별 폴더로 흩어지므로, Confluence UI에서 트리 탐색만으로 "전체 게시 문서"를 한 곳에서 훑어보기 어렵다. 라벨(태그) 검색이나 API 조회로는 여전히 전체를 조회할 수 있고, Tech Blog Viewer도 트리 탐색이 아니라 API/CQL로 동작하므로 기능적 영향은 없다. (검토됨·수용)
- **부수 효과(개선)**: 이 구조 변경을 계기로 "내 문서함" 목록도 초안만 보이던 기존 동작에서 초안+게시 문서를 함께 보여주도록 개선한다(게시해도 목록에서 사라지지 않고 상태 뱃지로 구분).

## 배경

기존 스캐폴딩은 "Space 홈페이지 하위 = 이메일 제목의 개인 폴더 = 그 하위 문서" 라는 1단계 구조뿐이었고, 게시(publish)는 문서를 별도 위치로 복사하는 것이 아니라 같은 페이지에 `isPublished` content property만 붙이는 방식이었다. 즉 초안이든 게시본이든 같은 Confluence 페이지가 항상 같은 자리에 있다.

이 서비스가 접근하는 Confluence Space는 IT팀 외 다른 직원도 열람 가능한 Space다. 따라서 초안이 다른 직원에게 노출될 수 있다는 문제가 있었고, 이를 포함해 태그, 게시 메타데이터의 확장성, 댓글 저장 구조까지 함께 설계했다.

## 확정된 요구사항

1. 초안(작성 중인 문서, 개인 폴더)은 작성자 본인 외 어떤 직원에게도 보이면 안 된다.
2. 게시하는 순간 제한이 해제되어 Space 구성원 누구나 볼 수 있어야 한다.
3. 문서 분류는 폴더 계층이 아니라 다중 태그로 한다.
4. 새 문서의 초기 내용은 지금처럼 빈 백지(제목+본문)로 유지한다 — 템플릿 도입 안 함(YAGNI).
5. 게시 메타데이터는 향후 다른 뷰어가 추가되어도 확장 가능한 구조로 잡는다(지금은 Tech Blog 하나뿐).
6. 댓글(footer comment) 기능은 이번 설계에 "저장 구조"로 포함한다. 다만 실제 API 연동은 별도 Viewer 프로젝트(자체 Confluence 자격증명 보유)의 책임이며, 이 프로젝트는 스키마만 정의한다.
7. 모든 Confluence 쓰기는 항상 공용 서비스 계정으로 이루어진다. AX Auth(MS) 로그인은 앱 사용자를 식별할 뿐 Confluence 상의 실제 신원과 무관하며, 실제 작성자 식별은 항상 content property로만 한다.
8. 아직 실사용 데이터가 없어 마이그레이션은 필요 없다.
9. (2026-08-24 추가) "내 문서함"은 초안·게시 문서를 함께 보여주고 상태 뱃지로 구분한다 — 게시해도 목록에서 사라지지 않는다.

## 검토한 접근법 — 초안 숨김 메커니즘

**접근법 A — 페이지별 Restriction, 직원 개인 계정 대상 (기각)**
문서/폴더 생성 시 작성자 개인의 Confluence accountId에 read/update 제한을 건다. Confluence Cloud는 GDPR 정책상 이메일로 계정을 조회하는 기능을 서비스 계정 권한으로 지원하지 않아, AX Auth 이메일 → Confluence accountId 매핑 수단이 없다. 기술적으로 막힐 가능성이 커 기각.

**접근법 B — 초안/게시됨 루트 분리 + 이동 (2026-08-21 채택 → 2026-08-24 개정으로 대체됨)**
Space 홈페이지 아래 "초안(Drafts Root)" / "게시됨(Published Root)" 두 루트 페이지를 두고, 게시 여부에 따라 문서 페이지를 두 루트 사이로 이동(parentId 변경)한다. 계정 매핑이 전혀 필요 없다.

이후 "계정 폴더가 먼저 오고 그 안에서 초안/게시를 나누는 편이 더 직관적"이라는 판단에 따라 접근법 B'(아래)로 대체됐다. 핵심 아이디어(계정 매핑 없이 페이지 이동 + 명시적 Restriction)는 그대로 유지되고, 트리에서 "초안/게시됨"과 "계정"의 상하 순서만 뒤바뀐다.

**접근법 B' — 계정 폴더 내부에서 초안/게시 서브폴더 분리 + 이동 (채택)**
Space 홈페이지 바로 아래에 계정(이메일) 폴더를 두고, 그 하위에 "초안"/"게시" 두 서브페이지를 둔다. 게시 여부에 따라 문서 페이지를 같은 계정 폴더 내 두 서브페이지 사이로 이동(parentId 변경)한다. 계정 매핑이 필요 없다는 장점은 그대로 유지되며, 추가로 관리자가 사전에 루트 페이지를 만들어 둘 필요도 없어진다(계정 폴더 생성 시 코드가 서브폴더까지 함께 만든다).

**접근법 C — Space 자체 분리 (기각)**
초안용/게시용 Space를 분리하는 방식. Space 생성은 보통 사이트 관리자 권한이 필요해 서비스 계정 권한 범위를 벗어날 가능성이 높고, 기존 코드의 "Space 1개" 가정을 크게 바꿔야 해 이번 단계에는 과함(YAGNI).

## 채택한 설계

### 전체 구조

```
Space 홈페이지
├── {author-email-1}  (계정 폴더 — 제한 없음, Space 공개)
│   ├── 초안           (서비스 계정 전용 제한)
│   │   ├── 문서 A (draft)
│   │   └── 문서 B (draft)
│   └── 게시           (제한 없음, Space 공개)
│       └── 문서 C (published)
└── {author-email-2}  (계정 폴더)
    ├── 초안
    └── 게시
```

- 계정 폴더는 지금까지의 "개인 폴더"와 같은 역할이지만, 이제 그 자체가 최상위이며 하위에 "초안"/"게시" 두 고정 서브페이지를 갖는다. 세 페이지(계정/초안/게시)는 계정 폴더가 처음 만들어질 때 한 번에 함께 생성된다 — 더 이상 관리자가 사전에 루트 페이지를 만들어 둘 필요가 없다.
- "게시" 서브페이지 하위는 평평한 목록이다(그 계정이 게시한 문서만, 추가 하위 폴더 없음) — 분류는 태그로 한다. 다만 이는 계정 단위로만 평평하고, Space 전체 관점에서는 작성자별로 나뉜다(아래 트레이드오프 참고).
- 게시(publish): 문서 페이지의 parent를 `{email}/초안` → `{email}/게시`로 변경(같은 계정 폴더 내 이동). 게시 취소는 반대로 이동.
- 관리자의 사전 수동 작업이 필요 없다 — 계정 폴더가 없는 사용자가 처음 로그인/문서 작성을 시도하면 코드가 계정 폴더+초안+게시 3개 페이지를 자동으로 만든다.

### 숨김 메커니즘 — 상속에 의존하지 않는 명시적 제한

최초 설계에서는 "부모 페이지의 Restriction이 하위 페이지에 상속된다"고 가정했으나, 이는 근거가 약한 가정이다. Confluence의 페이지 Restriction은 기본적으로 페이지별로 개별 적용되며, "이 아래 모든 페이지에 적용"은 그 순간 존재하는 하위 페이지에 일괄 복사하는 1회성 동작에 가깝다. API로 나중에 새로 만드는 페이지가 자동으로 상속받는다고 보장할 수 없다.

**보완된 방식**: 문서·서브폴더를 생성하는 시점에 그 페이지에 명시적으로 Restriction을 건다(상속을 신뢰하지 않음). 이 원칙은 계정 폴더 내부의 "초안" 서브페이지와 그 하위 문서에만 적용되고, 계정 폴더 자신과 "게시" 서브페이지·그 하위 문서에는 적용하지 않는다.

- 제한 대상은 **직원 개인 계정이 아니라 서비스 계정 자신**이다. 이미 구현된 `getCurrentConfluenceUser()`(`/rest/api/user/current`)로 서비스 계정의 accountId를 얻어 그 accountId만 read/update 허용 목록에 둔다.
- 이 방식은 직원 이메일 → Confluence 계정 매핑이 전혀 필요 없어, 접근법 A에서 문제였던 GDPR 제약을 그대로 피해간다.
- **제한 대상 페이지**: 계정 폴더 생성 시 만들어지는 "초안" 서브페이지, 그리고 그 하위에 새로 만들어지는 모든 문서.
- **제한하지 않는 페이지**: 계정 폴더 자신(이메일이 제목으로 노출됨), "게시" 서브페이지, 그 하위 문서. 게시 시 문서에 남아있던 제한을 제거하고, 게시 취소 시 다시 적용한다.
- 계정 폴더 자체를 열어 두기로 한 이유: (a) "게시" 서브페이지·문서에 조상 페이지의 제한이 실제로 영향을 주는지가 검증되지 않은 가정이라 굳이 그 위험을 새로 만들지 않는 편이 안전하고, (b) 이메일 노출은 초안 "내용" 비공개라는 핵심 보안 요건과는 별개의, 수용 가능한 수준의 노출로 판단했다.

### 태그

Confluence 네이티브 페이지 라벨(label) 기능을 사용한다. 커스텀 property를 새로 만들지 않고, Confluence의 라벨 검색(CQL `label = "..."`)을 그대로 활용한다. 다중 라벨 허용, 사전 정의된 카테고리 목록 없음(자유 텍스트).

### 내 문서함 — 초안+게시 통합 조회

계정 폴더 하위에 초안/게시가 함께 있으므로, "내 문서함" 조회 시 두 서브페이지의 자식을 모두 가져와 합친 뒤 각 문서에 상태(초안/게시됨)를 표시한다. 기존에는 개인 폴더(=초안 전용) 직계 자식만 나열해 게시한 문서가 목록에서 사라졌는데, 이번 구조 변경으로 자연스럽게 해소된다.

### 게시 메타데이터 — 뷰어별 확장 구조

```ts
interface PublishMetadata {
  isPublished: boolean;
  publishedAt?: string;
  viewers: {
    [viewerId: string]: {   // 예: "tech-blog"
      slug: string;
      metaDescription: string;
    };
  };
}
```

- 기존 `targetViewers: string[]` 필드는 제거하고 `Object.keys(viewers)`로 대체한다(중복 정보 제거).
- slug 중복 체크(`findPublishedPageBySlug`)는 뷰어별로 분리해서 검사한다 — 뷰어가 다르면 같은 slug를 써도 충돌이 아니다.
- 지금은 `viewers.tech-blog` 하나만 채우면 되고, 나중에 다른 뷰어가 생기면 같은 문서를 다른 slug/설명으로 그 뷰어에도 노출할 수 있다.

### 댓글 저장 구조 (스키마만 정의)

Viewer(별도 프로젝트)가 자체 Confluence 자격증명으로 직접 댓글을 쓰고 읽는다는 전제이므로, 여기서는 두 프로젝트가 공유해야 하는 저장 규칙만 정의한다.

- 댓글 본문은 `createFooterComment`의 `body.storage.value`(HTML)를 그대로 사용한다.
- 작성자 식별은 문서와 동일한 패턴 — 댓글 content에 딸린 content property로 저장한다.
  ```ts
  // property key: "commenterMeta", attached to the footer-comment's content id
  interface CommenterMeta {
    email: string;
    name: string;
    isEmployee: boolean; // AX Auth 로그인 여부
  }
  ```
- AX 로그인 상태면 `email`/`name`을 세션에서 채우고 `isEmployee: true`. 비로그인이면 사용자가 입력한 값을 그대로 저장하고 `isEmployee: false`.
- Confluence의 댓글 작성자(API 응답상 항상 Viewer의 서비스 계정)와 이 property의 `email`이 다르다는 점을 두 프로젝트가 공유해서 인지해야 한다.

## 검증이 필요한 가정 (구현 착수 전 스파이크로 확인)

1. Confluence v2 페이지 API(`PUT /api/v2/pages/{id}`)가 `parentId` 변경(페이지 이동)을 지원하는지. 지원하지 않으면 v1 API로 대체해야 한다.
   → ✅ 확인됨(2026-08-21). 실제 Confluence Cloud 인스턴스(space `ITTECHBLOG`)에 테스트 페이지 2개(부모용 1개, 이동 대상 1개)를 만들어 확인. `PUT /api/v2/pages/{id}`에 `{"id", "status":"current", "title", "parentId": "<새 부모 pageId>", "version": {"number": <현재+1>}}`를 보내면 200 응답과 함께 응답 바디의 `parentId`가 요청한 새 부모 ID로 실제 변경되었다. `parentType`도 `"page"`로 유지됨. 추가 파라미터나 v1 폴백 불필요.
2. 페이지 Restriction API가 v2에 없을 가능성이 높다 — 첨부파일 업로드가 이미 v1으로 대체된 전례처럼, v1 `/rest/api/content/{id}/restriction/byOperation/{read|update}`를 사용할 가능성이 크다.
   → ✅ 확인됨(2026-08-21). v2에는 restriction 엔드포인트가 없다(v1만 확인, v2 부재 자체를 별도로 테스트하지는 않음). v1 벌크 엔드포인트 `PUT /rest/api/content/{id}/restriction`에 `[{"operation":"read","restrictions":{"user":[{"type":"known","accountId":"<accountId>"}]}}, {"operation":"update","restrictions":{"user":[...]}}]` 형식(배열, `byOperation` 경로 아님)으로 보내면 200과 함께 각 operation의 restriction이 실제로 반영된 결과가 돌아온다. 이어서 `GET /rest/api/content/{id}/restriction`으로 재조회해도 동일하게 반영되어 있음을 확인. accountId는 `GET /rest/api/user/current`의 `accountId` 필드로 얻는다.
3. 서비스 계정 자신에게 거는 제한이 서비스 계정의 이후 API 호출 자체를 막지 않는지(제한 대상=자기 자신이므로 문제 없을 것으로 예상하지만 실제 확인 필요).
   → ✅ 확인됨(2026-08-21). 위 2번에서 테스트 계정 자신을 read/update restriction 대상으로 지정한 뒤, 같은 계정 자격으로 `GET /api/v2/pages/{id}?body-format=storage`를 호출하면 200이 정상적으로 반환되고 본문도 그대로 조회된다. 자기 자신에게 건 제한이 자기 API 호출을 막지 않음을 확인.
4. (2026-08-24 추가) 계정 폴더는 제한이 없고 그 하위 "초안" 서브페이지만 제한이 걸린 상태에서, "게시" 서브페이지·문서(제한 없음)를 Space 구성원이 실제로 열람할 수 있는지. 설계상 조상 페이지의 제한이 자손에 영향을 주지 않는다고 가정하지만(위 "숨김 메커니즘" 참고), 실제로는 "게시" 서브페이지도 같은 계정 폴더 하위이므로 확인이 필요하다.
   → ✅ 확인됨(2026-08-25). 실제 Confluence Cloud 인스턴스(space `ITTECHBLOG`)에 `createPersonalFolder`가 실제로 만드는 것과 동일한 구조(계정 폴더 1개 + 그 하위 "초안"/"게시" 2개, 총 3페이지)를 만들고 "초안"에만 서비스 계정 전용 read/update restriction을 건 뒤, `GET /rest/api/content/{id}/restriction`으로 세 페이지 각각의 restriction을 독립적으로 재조회했다. 결과: 계정 폴더·"게시" 두 페이지 모두 read/update restriction의 user 목록이 완전히 비어 있고(`size: 0`, Space 기본 권한 그대로 적용됨), "초안"만 서비스 계정 1명으로 정확히 제한되어 있었다 — 형제 페이지("초안")에 건 제한이 "게시"나 부모(계정 폴더)로 전혀 새어나가지 않음을 데이터 수준에서 확인했다. Confluence Cloud의 콘텐츠 제한은 각 페이지에 독립적으로 저장되는 속성이라 이 결과와 일치한다. 다만 이 확인은 서비스 계정 자격으로 각 페이지의 restriction 데이터를 직접 조회한 것이며, 서비스 계정이 아닌 실제 다른 직원 계정으로 "게시" 페이지를 로그인해 열람 가능한지까지는(제2의 실제 Confluence 계정이 없어) 클릭 테스트로 검증하지 못했다 — 다만 restriction이 완전히 비어 있으면 Space 기본 권한(구성원 열람 가능)이 그대로 적용된다는 것은 Confluence의 문서화된 표준 동작이다. 테스트 페이지 3개는 확인 후 즉시 trash+purge로 삭제했다.

이 4가지 모두 확인이 끝났다(1~3번은 Task 1 스파이크, 4번은 계정 폴더 구조 개정 후 별도로 확인. 테스트 페이지는 각 확인 후 즉시 trash+purge로 삭제).
