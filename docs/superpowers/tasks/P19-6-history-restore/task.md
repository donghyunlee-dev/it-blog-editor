# P19-6: 문서 이력에서 특정 버전으로 복원(되돌리기)

## 배경
P19-4/P19-5에 이어 사용자가 확인한 3가지 이력 확장 중 마지막(대화, 2026-09-18). 지금까지
읽기 전용이었던 이력 화면(P1-2a)에 처음으로 쓰기 동작이 추가되는 작업이라 범위를 신중하게
잡는다. Confluence는 과거 버전의 저장 형식(storage HTML) 본문을 내려주지만(P19-5에서 확인),
에디터는 지금 TipTap JSON → storage HTML 변환기(`tiptapDocToStorageFormat`)만 갖고 있고
반대 방향(storage HTML → TipTap JSON) 변환기가 없다 — 이 작업의 핵심 인프라다.

**실제 API로 확인한 사실(2026-09-18)**:
- 편집 원본을 담은 `sourceDocument` content property는 과거 버전을 별도로 보관하지 않는다
  — v1 레거시 API의 `?version=N` 파라미터로 직접 확인했으나, N값과 무관하게 항상 현재
  값만 돌아왔다(property의 `version.number`는 낙관적 잠금용 카운터일 뿐, 히스토리가
  아니다). 그래서 "편집 원본 JSON을 버전별로 그대로 되살리는" 방법은 없고, 반드시 저장
  형식(storage HTML)을 역변환해야 한다.
- 사용자 확인("컴포넌트를 그대로 원복할 수 있는지 검토 후 진행. 문서에 텍스트만 있을 리
  없다")에 따라 실제 저장 형식을 노드 타입별로 검토한 결과: **표·코드 블록·이미지·강조
  박스(패널)는 모두 원복 가능**(이미지·패널은 Confluence 전용 태그라 역변환기에서 별도
  처리 필요, 코드 블록은 언어 표시만 사소하게 유실). 반면 **"문서 링크 카드"(다른 문서를
  가리키는 카드)는 저장 시점에 원래 문서 ID를 알아볼 수 없는 순수 텍스트로만 남도록
  `tiptap-to-storage.ts`가 의도적으로 한쪽 방향만 구현돼 있어(P18-2 당시 결정), 복원해도
  카드가 아니라 안내 텍스트로만 돌아온다 — 이 한계는 사용자에게 안내하고 그대로 진행하기로
  확인됨(2026-09-18, "그 정도까지만 진행하자").
- **구현 중 실제 문서로 검증하다 발견한 버그**: 실제 Confluence는 `<ac:image>`의
  `<ri:attachment>`에 `ri:version-at-save` 같은, `<ac:structured-macro>`에
  `ac:schema-version`/`ac:macro-id` 같은 추가 속성을 스스로 덧붙인다 — 이 앱의
  `tiptap-to-storage.ts`는 이런 속성을 절대 만들지 않으므로, 그 형태만 가정한 첫 정규식은
  실제 문서(233439235)의 진짜 강조 박스·이미지를 인식하지 못했다(합성 라운드트립
  테스트로는 못 잡음 — 실제 문서 HTML로 직접 검증하다 발견). 정규식을 태그 끝까지
  관대하게(`[^>]*`) 고쳐 해결하고, 그 실제 HTML 형태를 그대로 옮긴 회귀 테스트를
  추가했다.
- **제목은 복원 대상에서 제외한다**: 문서 제목은 Confluence 버전이 아니라
  `sourceDocument` property에만 저장되는데, 이 property도 과거 버전을 보관하지 않는다
  (위 항목과 동일한 이유) — 그래서 "그 버전 시점의 제목"이라는 것 자체가 남아있지 않다.
  복원은 본문만 바꾸고 현재 제목은 그대로 유지한다.

## 수용 기준 (Acceptance Criteria)
- [x] 이력 화면에서 특정 과거 버전에 "이 버전으로 복원" 조작을 하면, 그 버전의 본문이
      현재 문서에 반영된다(제목은 위 이유로 범위에서 뺀다 — 현재 제목 유지).
- [x] 복원은 **비파괴적**이다 — 과거 버전을 지우거나 히스토리를 되감지 않고, 그 내용을
      담은 **새 버전**을 맨 위에 추가한다(Git/Notion/Google Docs의 "restore"와 같은 관례).
      복원 후에도 복원 이전 모든 버전이 이력에 그대로 남는다.
- [x] 복원 전 확인 Modal을 띄운다(`window.confirm()` 대신 — 프로젝트 UI 컨벤션,
      `docs/product/design.md`). 복원 성공/실패는 `Toast`로 안내한다.
- [x] 복원은 기존 저장 경로(`updateDocument`)의 낙관적 동시성 검사(`expectedVersion`)를
      그대로 통과해야 한다 — 복원하는 사이 다른 곳에서 문서가 먼저 바뀌었으면 기존과
      동일하게 충돌 오류를 띄운다(기존 저장 API를 그대로 재사용해 자동으로 만족).
- [x] storage HTML → TipTap JSON 변환기가 표·코드 블록(언어 표시 제외)·이미지·강조 박스
      (패널)를 손실 없이 복원한다 — "저장 → 변환 → 역변환 → 원본과 비교" 라운드트립
      테스트로 검증하고, 실제 문서(233439235)의 진짜 HTML로도 재검증했다. "문서 링크
      카드"만은 저장 형식 자체의 한계로 안내 텍스트로 복원된다는 것을 사용자에게
      확인받았다(위 "배경" 참고) — 이 노드 타입은 라운드트립 테스트에서 예외로 명시한다.
- [x] 복원 후 에디터 화면은 새로고침 없이 복원된 내용을 바로 보여준다(현재 편집 중이던
      저장되지 않은 변경사항이 있었다면, 복원으로 덮어써진다는 점을 확인 Modal 문구에
      명시한다) — `/editor/{pageId}`로 이동시켜 서버가 새로 저장된 내용을 다시 렌더링하게
      한다.

## 결정이 필요한 사항
없음. 다음은 코드베이스 관례·기존 동시성 설계를 근거로 이번 작업에서 직접 정한 구현
방식이며, 별도 GitHub Issue 없이 진행한다:
- 복원 = 새 버전 생성(비파괴적) — 기존 `updateDocument`의 버전 관리 방식과 그대로 맞물림.
- storage HTML → TipTap JSON 변환은 `@tiptap/core`의 `generateJSON`(연구 결과에 따라 확정)
  + 에디터가 쓰는 것과 동일한 확장 목록을 재사용 — 새 파서를 직접 구현하지 않는다.
- `generateJSON`은 브라우저 `DOMParser`가 있어야 동작해(서버는 `window`가 없음) 변환을
  클라이언트에서 한다 — 서버 API는 과거 버전의 원본 HTML만 내려주고(읽기), 변환된 결과를
  기존 저장 API(`PUT /api/editor/documents/{pageId}`)로 다시 보내는 건(쓰기) 그대로
  브라우저가 한다. 서버에서 변환하려면 `jsdom` 같은 무거운 DOM 폴리필을 새로 추가해야
  해서 피했다.

## 범위 밖
- 부분 복원(diff에서 일부 변경만 되돌리기) — P19-5 범위 밖과 동일.
- 복원 이력 자체를 구분 표시(예: "복원됨" 배지) — 최소 기능만 우선 구현하고, 필요하면
  후속 작업으로 추가한다.
