> 같다")으로 전용 페이지(`/welcome`) + 서버 리다이렉트 방식으로 다시 구현했다. 아래 수용
> 기준은 이 최종 방식 기준으로 갱신했다 — 원래 Modal 버전의 구현/검증 기록은 `result.md`/

## 배경
- Phase 5(사용자 계정 관리)의 두 번째 항목. P5-1(계정 데이터 모델 확장)에서 만든 `accountMeta`/`needsOnboarding`을 실제로 사용하는 첫 화면이다 — 이름·팀이 비어 있는 계정(신규 가입자, 또는 이 기능 도입 이전에 만들어진 기존 계정)이 로그인하면 메인(`/editor`)에 들어가기 전에 이름·팀을 입력받는다.
- 관련 문서: [prd.md의 Phase 5](../../../product/prd.md#-단계별-개발-계획)(P5-2), [prd.md 화면 정의의 "환영 페이지"](../../../product/prd.md#-화면-정의), [api-spec.md의 GET·PUT /api/editor/account](../../../product/api-spec.md), [design.md의 "온보딩 — Modal에서 전용 페이지로 전환"](../../../product/design.md)

## 수용 기준 (Acceptance Criteria)
- [ ] `GET /api/editor/account`가 세션 이메일의 계정 정보(`email`, `name`, `team`, `needsOnboarding`)를 반환한다.
- [ ] `PUT /api/editor/account`가 이름·팀을 저장한다. 이름 또는 팀이 비어 있으면(공백만 있는 경우 포함) 400(`INVALID_REQUEST`)을 반환한다.
- [ ] `needsOnboarding`이 true인 계정이 `/editor`로 들어오려 하면(로그인 직후 콜백이 항상 `/editor`로 보내므로 사실상 모든 첫 진입) `/editor/layout.tsx`가 `/welcome`로 서버 리다이렉트한다.
- [ ] `/welcome`은 로그인하지 않은 사용자를 `/login`으로, 이미 온보딩이 끝난 계정을 `/editor`로 각각 리다이렉트한다.
- [ ] `/welcome`에서 이름·팀을 저장하면 `/editor`로 이동한다(더 이상 `needsOnboarding`이 아니므로 이번엔 리다이렉트되지 않는다).
- [ ] 저장에 실패하면(예: 서버 오류) `/welcome`에 남아 오류 메시지를 보여준다.
- [ ] 위 API·페이지·컴포넌트 동작을 검증하는 자동화 테스트가 있다.

## 결정이 필요한 사항
없음 — Phase 5 착수 전 사용자와의 대화로 이미 확정([prd.md](../../../product/prd.md#phase-5--사용자-계정-관리-신규-2026-09-03-계획) 참고). 2026-09-03 온보딩 방식(Modal → 전용 페이지) 변경도 사용자 피드백으로 바로 확정됨.

## 범위 밖
- 접속 권한 게이트(로그인은 됐지만 접속 차단된 계정을 막는 것)는 P5-3에서 다룬다.
- 로그인 후 언제든 이름·팀을 다시 수정하는 계정 정보 팝업(별도 진입점, Modal 유지)은 P5-4에서 다룬다 — 이 항목은 온보딩(최초 1회, 강제) 흐름만 다룬다. 다만 저장에 쓰는 API(`PUT /api/editor/account`)는 두 항목이 공유한다. "메인에서 팝업으로 받지 않는다"는 이번 피드백은 강제 온보딩에 한정된 지적이라, 사용자가 원할 때 스스로 여는 계정 정보 수정 팝업까지 페이지로 바꿀 필요는 없다고 판단했다.
- 계정 표시 형식("이름(이메일)") 통일은 P5-5에서 다룬다.
- AX Auth 로그인 콜백(`/api/auth/ax-callback`) 자체를 바꿔 로그인 직후 바로 `/welcome`으로 보내는 방식은 검토했으나 채택하지 않았다 — 콜백에 도메인 조회(계정 존재·온보딩 여부) 책임을 얹기보다, 이미 그 책임을 지고 있는 `/editor/layout.tsx`가 판단해 리다이렉트하는 편이 계층 원칙(architecture.md)에 맞다.
