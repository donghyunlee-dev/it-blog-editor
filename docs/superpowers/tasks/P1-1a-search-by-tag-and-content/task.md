# P1-1a: 사이드바 검색을 태그·본문까지 확장

## 배경
2026-08-27 [프로덕션 준비도 감사](https://claude.ai/code/artifact/87302c07-68d6-42ed-8712-9345547cb659)에서 P1로 지적된 항목. `EditorSidebar.tsx`의 검색은 문서 제목 부분일치만 확인한다(`EditorSidebar.tsx:128-130`).

## 조사 결과 — "본문 검색"은 이 항목에서 함께 구현하지 않는다
사이드바가 받는 `documents: DocumentSummary[]`(`src/lib/editor/documents.ts`)는 `{ pageId, title, updatedAt, isPublished, tags }`만 담고 있고 본문(TipTap JSON, `sourceDocument` property)은 포함하지 않는다. 이유는 `listDocuments()`가 이미 문서마다 태그를 별도로 조회하는 N+1 패턴이기 때문이다(`api-spec.md`가 "문서 수가 개인 단위라 N+1 호출을 허용"이라고 명시). 본문까지 검색하려면 문서마다 `sourceDocument` property를 추가로 조회해야 해서, 이미 알려진 N+1 비용을 사실상 두 배로 늘린다 — 이는 P0-5a/P1-1c가 이미 다루고 있는 "문서 수 증가에 따른 성능" 문제와 정확히 같은 종류의 트레이드오프이므로, 값을 임의로 정하지 않고 별도 결정을 받는다([Issue 등록 — 아래 "결정이 필요한 사항" 참고]).

이번 항목은 감사에서 지적된 것 중 **비용 없이 즉시 가능한 부분**(태그 검색 — 이미 `DocumentSummary.tags`로 클라이언트에 내려와 있어 추가 조회가 필요 없다)만 구현한다.

## 수용 기준 (Acceptance Criteria)
- [ ] 사이드바 검색어가 문서 제목에 포함되거나, 문서에 붙은 태그 중 하나라도 검색어를 포함하면 그 문서를 보여준다(대소문자 구분 없이, 기존 제목 검색과 같은 방식).
- [ ] 태그 필터 칩(`activeTag`)과 검색어 필터는 지금처럼 함께(AND) 적용된다 — 이번 변경이 기존 태그 필터 동작을 바꾸지 않는다.
- [ ] 검색 입력의 스크린리더 라벨을 "문서 제목 검색"에서 실제 동작(제목+태그)에 맞게 갱신한다.

## 결정이 필요한 사항
- [ ] 본문(문서 내용) 검색을 지원할지, 지원한다면 어떤 방식으로 할지(문서 목록 조회 시 본문까지 함께 가져올지 — N+1 비용 증가 — vs. 검색어를 입력했을 때만 그때그때 서버에 물어보는 별도 검색 API를 새로 만들지 vs. 진짜 검색 색인을 도입할지) — GitHub Issue로 등록해 결정을 받는다.
