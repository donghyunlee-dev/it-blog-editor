# P1-5: 민감 API 엔드포인트에 레이트리밋을 추가한다

## 배경
- 2026-08-27 [프로덕션 준비도 감사](https://claude.ai/code/artifact/87302c07-68d6-42ed-8712-9345547cb659)에서 나온 항목. 문서 생성·이미지 업로드·게시 API에 요청 빈도 제한이 전혀 없었다.
- 구현 방식과 임계값 모두 결정이 필요해 [Issue #5](https://github.com/sfood-pioneer-1st/sfood-it-editor/issues/5)로 등록했다. 2026-08-31 "사용자가 많지 않고 동시 사용률이 높지 않아 단일 인메모리 방식"으로 방식만 답변됐고, 임계값(엔드포인트별 분당 허용 횟수)은 이슈 답변에 없어 2026-09-03 대화로 직접 확인했다 — **사용자당 분당 30회**.

## 수용 기준 (Acceptance Criteria)
- [x] 단일 프로세스 메모리 기반 고정 윈도우 레이트리밋 유틸리티를 추가한다(외부 스토어 없음).
- [x] 문서 생성(`POST /api/editor/documents`), 이미지 업로드(`POST /api/editor/documents/[pageId]/images`), 게시(`PATCH /api/editor/documents/[pageId]/publish`) 세 엔드포인트에 적용한다.
- [x] 임계값은 사용자(세션 이메일)당 분당 30회, 엔드포인트별로 독립적으로 집계한다.
- [x] 초과 시 429(`RATE_LIMITED`)를 반환하고 `Retry-After` 헤더로 다음 윈도우까지 남은 초를 알린다.
- [x] 레이트리밋 검사는 세션 확인 직후, 실제 도메인 작업(폴더 조회·소유자 검증·Confluence 호출 등) 전에 이뤄져 초과 시 불필요한 후속 작업을 하지 않는다.

## 결정이 필요한 사항
없음 — Issue #5(방식) + 2026-09-03 대화(임계값)로 모두 확정됐다.

## 범위 밖
- 다중 인스턴스 배포 시 인스턴스별로 카운터가 분리되는 한계는 Issue #5에서 이미 받아들이기로 한 것이라 이번 작업에서 다루지 않는다(AWS 배포 방식이 오토스케일링으로 바뀌면 재논의 대상).
- 레이트리밋 대상이 아닌 나머지 API(조회 계열 GET 등)는 대상이 아니다 — 감사 리포트가 지목한 "문서 생성·이미지 업로드·게시" 세 곳만 다룬다.
