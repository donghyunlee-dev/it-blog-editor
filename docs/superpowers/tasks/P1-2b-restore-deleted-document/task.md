# P1-2b: 삭제된 문서 복구 기능

## 배경
2026-08-27 [프로덕션 준비도 감사](https://claude.ai/code/artifact/87302c07-68d6-42ed-8712-9345547cb659)에서 P1로 지적된 항목. `deleteDocument`는 Confluence 페이지를 휴지통으로 옮길 뿐(소프트 삭제, `src/lib/confluence/client.ts`의 `deletePage` 주석 참고)인데, 이 애플리케이션에는 되돌릴 방법이 전혀 없다. 실수로 삭제 버튼을 누르면 영구히 사라진 것처럼 보인다.

## 설계 결정: 자체 "삭제된 문서" 레지스트리를 둔다
Confluence 휴지통에 들어간 페이지를 `status=trashed` 같은 조건으로 나열해 "이 계정 소유 문서"만 걸러내는 API 동작(정렬·필터 조합)은 이 환경에서 실제 인스턴스로 검증하지 못했다. 대신 이미 이 프로젝트가 쓰고 있는 패턴(`P0-5a`의 slug 인덱스처럼 "우리가 직접 알고 있는 상태를 저장해두고 그것만 신뢰") 그대로, **삭제 시점에 계정 폴더(`accountFolderId`) 페이지의 `deletedDocuments` content property에 `{pageId, title, deletedAt}`를 직접 기록**해 목록을 만든다. 이렇게 하면 "휴지통 안의 페이지를 어떻게 질의하는가"라는, 검증 안 된 넓은 표면적을 피하고, 검증이 필요한 부분을 "휴지통에 있는 특정 pageId 하나를 다시 꺼낼 수 있는가"(아래) 하나로 좁힌다.

## 이 작업을 PR로 진행하는 이유
복구는 결국 `movePage(pageId, draftFolderId)`(기존 함수, `status: "current"`로 고정해서 PUT하는 로직을 이미 갖고 있음)를 트래시된 페이지에 그대로 호출하는 방식으로 구현한다. 즉 "트래시 상태의 페이지에도 `GET /api/v2/pages/{id}`가 정상 동작하고, 그 결과에 PUT으로 `status: 'current'`를 실어 보내면 실제로 복구되는가"라는, Atlassian 공식 문서 근거로만 구현하고 실제 인스턴스로는 확인하지 못한 가정이 남는다. P1-2a와 같은 이유로 main에 직접 반영하지 않고 PR로 올린다.

## 수용 기준 (Acceptance Criteria)
- [ ] 문서를 삭제하면(`deleteDocument`) 삭제 직전 상태(pageId, 제목, 삭제 시각)가 작성자 계정 폴더의 레지스트리에 기록된다.
- [ ] 사이드바에 "삭제된 문서" 진입점(버튼)이 있고, 클릭하면 본인이 삭제한 문서 목록을 보여주는 Modal이 뜬다(제목 + 삭제 시각).
- [ ] 목록의 각 항목에 "복구" 버튼이 있고, 누르면 해당 문서가 "초안" 서브폴더로 되돌아오고(작성자 본인 전용 제한도 다시 적용), 문서함 목록에 다시 나타난다.
- [ ] 복구에 성공하면 레지스트리에서 해당 항목이 제거된다.
- [ ] 남의 문서는 이 레지스트리에 보이지도, 복구할 수도 없다 — 항상 로그인한 사용자 본인의 계정 폴더 레지스트리만 읽고 쓴다(다른 라우트처럼 `requireDocumentOwner`를 그대로 쓰지 않는 이유: 트래시된 페이지에서 `authorMeta` property를 다시 읽을 수 있는지 자체가 미검증이라, 소유권 판단을 레지스트리 소속 여부로만 하도록 범위를 좁혔다).
- [ ] Confluence 휴지통이 일정 기간 후 영구 삭제(purge)해 이미 실제로는 없는 문서를 복구하려 하면(404), 오류 메시지를 안내하고 레지스트리에서도 그 항목을 제거한다(빈 화면으로 방치하거나 무한히 재시도 가능한 죽은 항목으로 남기지 않는다).

## 결정이 필요한 사항
없음. 다만 아래 2가지는 스스로 판단해 정한 기본값이며, 필요하면 이후 별도 항목으로 재논의한다(PR 설명에도 명시):
- 복구된 문서는 이전에 게시 상태였더라도 항상 "초안"으로 돌아온다(즉시 재공개하지 않음) — 삭제 당시 게시 여부를 신뢰할 근거(트래시 상태에서 `publishMetadata` property를 다시 읽을 수 있는지도 미검증)가 약하므로, 더 안전한 쪽(비공개)을 기본값으로 택했다.
- 레지스트리에 보관 기간 제한(예: 30일 후 자동 정리)은 두지 않는다 — Confluence 자체 휴지통 보관 정책에 맡긴다(실제로 purge되면 위 마지막 수용 기준으로 정리됨).

## 범위 밖
- 레지스트리 자체의 이력 조회(누가 언제 무엇을 삭제했는지 감사 로그) — 지금은 "현재 복구 가능한 것"만 보여준다.
- Confluence 휴지통을 직접 순회하는 방식(위 "설계 결정" 참고) — 향후 P0-5b처럼 구조적으로 다시 다룰 수 있는 여지를 남긴다.
