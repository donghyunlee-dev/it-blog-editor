# P0-8: 게시 여부를 폴더 이동이 아니라 property만으로 관리하도록 단순화한다

## 배경
P0-7 작업 중 사용자가 "Confluence는 DB 역할이고, 페이지를 직접 열어보는 건 관리자만 가능하면 된다"고 결정했다(2026-08-28). 이 결정 직후 사용자가 이어서 질문했다: "계정별 초안, 게시 2개를 구분해서 나눠서 페이지 이동을 시킬 필요가 있을까? properties에 게시 여부를 설정하면 되지 않을까?"

기존 설계([2026-08-21 Confluence 콘텐츠 구조 설계](../../superpowers/specs/2026-08-21-confluence-content-structure-design.md))를 다시 확인한 결과, 계정 폴더 하위에 "초안"/"게시" 두 서브폴더를 두고 게시할 때마다 문서를 그 사이로 물리적으로 이동(`movePage`)시켜온 이유는 세 가지였다:
1. **사람이 Confluence 트리를 직접 탐색해 초안/게시를 구분해볼 거라는 전제** — 설계 문서에 "게시된 문서가 흩어지면 트리 탐색만으로 전체 게시 문서를 훑어보기 어렵다"는 트레이드오프가 실제로 명시돼 있다. 이번 "아무도 직접 안 본다" 결정으로 이 전제 자체가 사라졌다.
2. **`listDocuments()`가 별도 property 조회 없이 폴더 위치만으로 게시 여부를 판단** — 이미 P0-7로 문서마다 `sourceDocument`를 추가 조회하고 있어 "폴더 위치가 공짜"라는 이점이 예전만큼 크지 않다.
3. **`setPublishState()`의 재시도 안전성** — "저장된 `publishMetadata.isPublished` 플래그가 아니라 실제 페이지 위치로 판단"하는 방식으로, 메타데이터 기록이 실패해도 재시도가 항상 안전하게 수렴하게 했다.

세 이유 모두 이제 사라졌거나 대체 가능하다고 판단해(대화로 분석·합의, 2026-08-28) 폴더 이동 메커니즘 자체를 제거하기로 했다. "지금은 개발 초기 단계라 PRD 문서 정리와 규칙을 잡아야 한다"는 사용자 판단에 따라, 이미 완료 표시된 Phase 1 기능("초안-게시 생명주기")을 되돌리더라도 지금 바로잡기로 한다.

## 수용 기준 (Acceptance Criteria)
- [ ] 계정 폴더 하위에 "초안"/"게시" 서브폴더를 더 이상 만들지 않는다 — 계정 폴더 하나에 모든 문서(초안·게시 구분 없이)가 있다.
- [ ] 게시/게시취소는 문서를 이동시키지 않고, restriction(제한) 적용/해제 + `publishMetadata.isPublished` 갱신만으로 이뤄진다.
- [ ] `listDocuments()`가 계정 폴더 하나만 조회하고, 게시 여부는 `publishMetadata.isPublished` property로 판단한다.
- [ ] 삭제된 문서를 복구(P1-2b)하면 계정 폴더로 이동하고, **restriction을 다시 걸며 `publishMetadata.isPublished`도 `false`로 되돌린다**(중요 — 이전에는 "초안 폴더로 이동"이 곧 "미게시 상태로 되돌림"이었는데, 폴더 구분이 없어지면 이 둘을 각각 명시적으로 해줘야 한다. 안 하면 게시 중이던 문서가 복구 후 restriction은 걸려 있는데(비공개) `publishMetadata.isPublished`는 `true`로 남아(자기모순) 화면에 "게시됨"으로 잘못 표시된다).
- [ ] 새 문서는 항상 restriction이 걸린(작성자 본인 전용) 상태로 시작한다(기존 "초안" 상태와 동일한 보안 속성 유지).
- [ ] 기존 API 요청/응답 스키마(`title`/`doc`/`version` 등)는 바뀌지 않는다 — 내부 구현(폴더 구조)만 바뀐다. 다만 `GET/POST /api/editor/folder`의 응답에서 `draftFolderId`/`publishedFolderId`는 제거된다(프런트엔드에서 이 필드를 쓰는 곳이 없음을 확인했다).
- [ ] 기존 P1-2b(복원) 관련 회귀가 없어야 한다.

## 결정이 필요한 사항
없음 — 사용자가 대화로 직접 방향을 결정했고, "재시도 안전성" 대체 방안(restriction 적용을 property 기록보다 먼저 하고, restriction 자체가 멱등 연산이라는 점에 기댄다)은 기존 P0-3/P0-6 등에서 이미 써온 "완전한 원자성은 불가능하니 감지 가능/자기수렴 가능한 수준까지"라는 원칙을 그대로 적용한 것이라 새로운 논의가 필요 없다고 판단했다.

## 범위 밖
- P1-10(복원 시 계정 폴더 밖으로 이동하는 기존 버그)의 근본 원인 확정 — 이번 리팩터로 "어느 서브폴더로 이동할지 고르는" 코드 경로 자체가 사라져 그 버그가 발생할 여지도 함께 없어지는 것으로 보이지만, 원래 버그의 정확한 원인을 소급해서 확인하지는 않는다. PRD의 P1-10 항목은 "이번 리팩터로 재현 경로가 사라짐"으로 갱신하되, 이 리팩터 이전에 만들어진 pageId `212959235`(실제로 계정 폴더 밖에 있는 문서) 자체를 수동으로 옮기는 정리 작업은 하지 않는다.
- 이 저장소 밖의 Tech Blog Viewer 프로젝트에 미치는 영향 — 게시 여부 판단 방식이 바뀌어도 Viewer가 이미 `publicSlug`/`isPublished` 등 API 응답 필드를 그대로 쓰고 있다면 영향이 없을 것으로 보이지만, 이 저장소가 통제할 수 있는 범위가 아니다.
- 기존에 이미 만들어진 계정 폴더(예: `donghyun.lee@s-food.com`)의 "초안"/"게시" 서브폴더 정리(삭제) — 코드가 더 이상 이 서브폴더들을 만들지도 참조하지도 않게 될 뿐, 기존에 남아있는 빈 서브폴더를 능동적으로 지우지는 않는다(실사용 데이터가 사실상 없다는 기존 판단과 동일).
