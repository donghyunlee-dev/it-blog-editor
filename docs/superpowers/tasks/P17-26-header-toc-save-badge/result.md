# P17-26: 헤더 버튼·TOC 경계 여백 정렬 + 저장 상태 뱃지화 — 구현 결과 보고서

## 구현 내용
1. **경계선 기준 좌우 여백 정렬**: 임시 디버그 라우트에서 실측한 결과, 본문↔TOC
   경계선을 기준으로 헤더 버튼 클러스터는 24px(`px-6`)만 떨어져 있는데 TOC의 "이
   페이지" 콘텐츠는 48px(`pl-12`)나 떨어져 있어 정확히 2배 차이였다. 이 비대칭이
   "버튼 위치가 정돈되지 않은 느낌"의 실체였다. `TableOfContents.tsx`의 TOC 콘텐츠
   왼쪽 여백을 `pl-12`(48px) → `pl-6`(24px)로 줄여 헤더 버튼과 맞췄다. TOC 상단의
   96px 공백(헤더 높이 56px + 40px, 본문 제목과의 정렬용)은 사용자 확인에 따라 그대로
   유지했다.
2. **저장 상태 뱃지화**: `DocumentEditor.tsx`의 `SaveStatusIndicator`가 순수 텍스트
   (`<span>`)로 그리던 저장 상태를 `@sfood/ui`의 `Badge` 컴포넌트(배경·테두리가 있는
   알약 모양)로 바꿨다. `StatusBadge`(점+텍스트, 배경 없음)도 검토했지만 사용자가
   명시적으로 요청한 "뱃지 형식"에는 `Badge` 쪽이 맞아 채택했다. 상태별 색:
   저장 중=`info`, 변경사항 있음=`warning`, 저장됨=`success`(기존에도 저장됨만
   `text-success`였던 것과 같은 의미, 나머지 두 상태에도 색을 명시적으로 부여).
   반응형 숨김(`hidden sm:flex`)은 Badge 자신의 기본 `inline-flex`와 충돌하지 않도록
   바깥의 별도 `<span>`으로 분리했다.
3. **헤더 버튼 그룹핑(구분선 도입)**: 대화 중 제안했으나, 배지화만으로 이미 충분히
   정돈되어 보인다는 사용자 판단에 따라 **진행하지 않음**.

## 자체 검토 (Self-Review)
### 긍정 사항
- "조잡스럽다"는 주관적 리포트를 곧바로 코드 수정으로 연결하지 않고, 실측
  (`getBoundingClientRect`)으로 정량화한 뒤 사용자에게 구체적인 수치(24px vs 48px)로
  확인받아 진행했다 — 추측성 변경이 없었다.
- 저장 상태 뱃지는 새 컴포넌트를 만들지 않고 이미 이 프로젝트가 다른 화면
  (`/editor/accounts`)에서 쓰는 `@sfood/ui`의 `Badge` 계열 컴포넌트를 재사용했다
  (CLAUDE.md 우선순위 ① 원칙).
- 헤더 버튼 그룹핑처럼 처음엔 필요해 보였던 항목도, 사용자가 "이미 충분하다"고
  판단하면 억지로 진행하지 않고 범위에서 뺐다 — 과잉 구현을 피했다.

### 주의사항
- `/editor/[pageId]`가 AX Auth(MS SSO) 로그인 뒤에 있어 실제 로그인 세션에서의 최종
  화면은 이 세션에서 직접 보지 못했다 — 임시 디버그 라우트(검증 후 삭제)에서의 실측/
  스크린샷으로 대체했다.
- 헤더 버튼 그룹핑은 이번엔 진행하지 않았지만, 나중에 버튼이 더 늘어나면(예: 새 헤더
  액션 추가) 다시 검토가 필요할 수 있다.

### 우려사항
- 없음 — 클래스 값 변경(`pl-12`→`pl-6`)과 컴포넌트 교체(텍스트→`Badge`) 모두 구조를
  바꾸지 않는 국소적 변경이라 회귀 위험이 낮다. 관련 테스트(DocumentEditor 46개,
  TableOfContents/EditorShell 포함 86개) 전부 통과.
