# P1-8: 삽입된 이미지에 대체 텍스트(alt) 입력 UI 추가

## 배경
- 2026-08-27 [프로덕션 준비도 감사](https://claude.ai/code/artifact/87302c07-68d6-42ed-8712-9345547cb659)에서 나온 항목으로, `docs/product/prd.md`의 Phase 4 P1 체크리스트 "삽입된 이미지에 대체 텍스트(alt)를 입력할 수 있는 UI를 추가한다"에 해당한다.
- 현재 에디터는 드래그앤드롭·붙여넣기·슬래시 메뉴 세 경로 모두 `insertUploadedImage()`(`src/components/editor/RichTextEditor.tsx`)로 이미지 노드를 만들지만 `src`/`filename`만 채우고 `alt`는 항상 비어 있다. TipTap의 `@tiptap/extension-image` 스키마 자체는 `alt` 속성을 이미 갖고 있어(`AttachmentImage`가 `filename`만 추가로 확장) 화면에는 `<img alt="">`로 렌더링되고 있다 — 스크린리더 사용자에게 이미지 내용이 전달되지 않는다.
- Confluence storage format 변환기(`src/lib/editor/tiptap-to-storage.ts`)도 `alt`를 전혀 참조하지 않아, 설령 값이 있어도 저장되지 않는다.

## 수용 기준 (Acceptance Criteria)
- [x] 에디터에서 이미지를 클릭(선택)하면 alt 텍스트를 입력할 수 있는 UI(플로팅 팝업)가 뜬다.
- [x] 입력한 값을 적용하면 해당 이미지 노드의 `alt` 속성이 갱신되고, 문서를 저장했다가 다시 불러와도(TipTap JSON에 값이 남아) 유지된다.
- [x] alt가 설정된 이미지는 에디터 렌더링에서 실제 `<img alt="...">`로 나타난다(TipTap 기본 스키마 동작 확인만 필요, 별도 렌더링 코드 없음).
- [x] alt 값이 있는 이미지를 Confluence storage format으로 변환하면 `<ac:image ac:alt="...">`로 직렬화된다(첨부파일 참조·외부 URL 참조 두 경로 모두). 값이 없으면 기존과 동일하게 `ac:alt` 속성 자체를 넣지 않는다.
- [x] alt 입력은 선택 사항이다 — 비워두면 기존과 동일하게 동작하고 에러가 발생하지 않는다.
- [x] 이미지가 아닌 텍스트를 선택했을 때는 기존 서식 버블 메뉴(굵게/기울임/색상 등)만 뜨고 alt 입력 UI는 뜨지 않으며, 반대로 이미지를 선택했을 때는 서식 버블 메뉴가 뜨지 않는다(현재는 이미지 선택 시에도 텍스트 버블 메뉴가 함께 뜨는 부수 효과가 있음 — 이번 작업에서 함께 바로잡는다).

## 결정이 필요한 사항
없음 — alt 텍스트 입력 UI 형태(선택 시 뜨는 플로팅 팝업)와 필수/선택 여부(선택 사항)는 P1-6a/P1-6b/P1-6c와 같은 근거로 순수 UX 판단이라 GitHub Issue 없이 직접 정한다: 이미지는 alt가 없어도 문서 자체는 유효하고, 강제하면 기존 문서(이미 삽입된 이미지들)에 대한 마이그레이션 부담이 생기기 때문이다.

## 범위 밖
- alt 자동 생성(이미지 인식·OCR 등)은 다루지 않는다.
- 공개 뷰어(Tech Blog) 쪽에서 `ac:alt`를 실제로 어떻게 렌더링하는지는 이 저장소 밖(별도 Viewer 프로젝트) 관심사라 확인하지 않는다.
- alt 텍스트 길이 상한·서버 측 검증은 다루지 않는다 — Confluence storage format의 `ac:alt`가 특별한 길이 제약을 두지 않고, alt는 사용자가 자유롭게 쓰는 설명문이라 제목/태그(P1-6a/b)처럼 URL 라우팅이나 UI 레이아웃 안전성과 직결되는 값이 아니다. 다만 극단적으로 긴 입력이 UI를 깨는 것만 막기 위해 입력창에 `maxLength` 정도의 가벼운 클라이언트 가드는 둘 수 있다(서버 검증 아님).
