# P19-1: 문서 "이력"을 Modal에서 전용 페이지로 전환

## 배경
사용자 지적 — "히스토리를 보는 방법이 팝업이라서 리스트가 안 보이는 문제가 있어. 삭제된
문서처럼, 히스토리도 팝업이 아닌 페이지에 리스트를 보여주는 방식으로 변경해야 해." "삭제된
문서" 기능은 이미 P16-1(`docs/superpowers/tasks/P16-1-deleted-documents-page/task.md`)에서
같은 이유(목록이 늘어날수록 팝업으로는 감당이 안 됨)로 `Modal` → 전용 페이지(`/editor/trash`)
전환을 마쳤다. 이 작업은 "이력"(`VersionHistory.tsx`, P1-2a) 기능에 동일한 전환을 적용한다.

관련 문서: `docs/product/prd.md` P14-2(사이드바 옵션 메뉴로 "이력" 이동, 당시엔 Modal 유지),
P16-1(삭제된 문서 Modal→페이지 전환의 선례).

## 수용 기준 (Acceptance Criteria)
- [ ] 사이드바 문서 옵션(⋯) 메뉴의 "이력"을 누르면 Modal이 아니라 `/editor/history/{pageId}`
      페이지로 이동한다.
- [ ] 이 페이지는 `/editor/trash`와 같은 패턴(서버 컴포넌트가 목록을 미리 조회해
      `initial*` prop으로 내려주고, 클라이언트에서 마운트 후 별도 fetch를 하지 않음)으로
      구현된다.
- [ ] 페이지는 버전 번호·생성 시각(`YYYY.MM.DD HH:mm`)·현재 버전 여부를 기존 Modal과
      동일하게 보여준다(읽기 전용 — 되돌리기 등 쓰기 동작 없음, P1-2a 범위 유지).
- [ ] 버전이 없으면 `@sfood/ui`의 `EmptyState`로 안내한다(트래시 페이지와 동일한 컴포넌트
      사용).
- [ ] 본인 문서가 아니거나(공유받았지만 접근 권한 없음) 존재하지 않는 pageId로 접근하면
      기존 `requireDocumentAccess`/`NotFoundError` 처리와 동등한 방식으로 막는다.
- [ ] 기존 `GET /api/editor/documents/{pageId}/versions` 라우트는 그대로 둔다(삭제된 문서의
      `GET /api/editor/documents/deleted`도 클라이언트에서 안 쓰이지만 유지되는 것과 같은
      선례 — API 계약을 건드리지 않는다).

## 결정이 필요한 사항
없음 — 사용자가 대화에서 "삭제된 문서 페이지와 동일한 패턴"으로 확정함(검색 입력은 트래시
페이지의 제목/태그 검색에 대응하는 필드가 이력 목록엔 없어 포함하지 않음 — 아래 "범위 밖"
참고).

## 범위 밖
- 검색/필터 입력: 트래시 페이지의 검색은 제목·태그를 대상으로 하는데, 버전 이력 항목에는
  그런 속성이 없어(버전 번호·시각뿐) 추가하지 않는다.
- 페이지네이션/무한스크롤: 트래시 페이지도 페이지네이션이 없고, 사용자가 명시적으로
  "삭제된 문서 페이지와 동일한 패턴"(페이지네이션 없음)을 선택했다.
- 버전 되돌리기(restore) 등 쓰기 동작: P1-2a 때부터 범위 밖으로 명시된 것을 유지한다.
- 자동저장 시 히스토리가 불필요하게 늘어나는 문제 자체는 별도 작업(P19-2, dedup 저장)에서
  다룬다.
