# P1-1c: 문서 목록 페이지네이션/무한스크롤 도입

## 배경
2026-08-27 [프로덕션 준비도 감사](https://claude.ai/code/artifact/87302c07-68d6-42ed-8712-9345547cb659)에서 P1로 지적된 항목. `listDocuments()`가 한 사용자의 초안+게시 문서 전체를 한 번에 불러오고, 사이드바는 그 전체를 한 번에 DOM에 그린다 — 문서 수가 늘어나면 목록이 무거워진다.

## 조사 결과 — 이번 항목이 다루는 범위
`listDocuments()`는 `EditorSidebar` 표시용으로만 쓰이는 게 아니라, `tag-suggestions.ts`의 태그 자동완성(`listTagSuggestions`)도 "작성자가 쓴 모든 태그"를 구하기 위해 **같은 함수**를 호출해 전체 목록을 필요로 한다(`src/lib/editor/tag-suggestions.ts:27`). 그래서 `listDocuments()` 자체(서버가 Confluence에 요청하는 범위)를 진짜로 페이지네이션하려면, 태그 자동완성이 여전히 전체 태그 목록을 구할 다른 방법(예: 태그 전용 조회 API)을 먼저 마련해야 한다 — 이는 이미 알려진 N+1 조회 비용 문제(`data-spec.md`, P0-5a/P1-1a의 결정 대기 항목들)와 같은 아키텍처 질문이라 이번 항목에서 함께 풀지 않는다.

이번 항목은 **화면(사이드바) 쪽의 문제**만 다룬다 — 서버가 이미 다 불러온 목록을(어차피 태그 자동완성 때문에 다 불러와야 한다) 사이드바가 한 번에 전부 그리지 않고, 일부만 먼저 보여준 뒤 "더 보기"로 나머지를 점진적으로 그리게 한다. 이건 Confluence 호출 횟수를 줄이지는 못하지만(그 부분은 별도 결정 필요), 문서가 아주 많을 때 사이드바 DOM 크기·스크롤 부담을 줄이는 실질적 효과가 있다.

## 수용 기준 (Acceptance Criteria)
- [ ] 태그 필터·검색어·정렬을 모두 적용한 결과 중 처음 30개만 먼저 렌더링한다.
- [ ] 30개보다 결과가 많으면 목록 아래에 "더 보기" 버튼이 나타나고, 누르면 다음 30개가 추가로 렌더링된다(반복 가능).
- [ ] 결과가 30개 이하면 "더 보기" 버튼 자체가 나타나지 않는다.
- [ ] 검색어·태그 필터·정렬을 바꾸면 다시 처음 30개부터 보여준다(이전 "더 보기"로 늘려둔 상태가 새 조건에는 이어지지 않는다) — 그렇지 않으면 필터를 바꿨는데 갑자기 없던 문서가 우르르 나타나거나, 있어야 할 문서가 다음 페이지에 숨어 안 보이는 혼란이 생긴다.

## 결정이 필요한 사항
없음 — 서버 쪽 N+1 조회 비용을 줄이는 근본적인 해결(태그 자동완성을 별도 경로로 분리하고 `listDocuments` 자체를 진짜로 페이지네이션하는 것)은 이미 알려진 아키텍처 질문(P0-5a/P1-1a 결정 대기 항목들과 같은 종류)이라 이번엔 다루지 않는다. 필요해지면 별도 항목으로 논의한다.

## 범위 밖
- 서버 측(Confluence 호출 자체)의 페이지네이션 — 위 "조사 결과" 참고.
- 무한스크롤(IntersectionObserver 기반 자동 로드) — "더 보기" 버튼 방식을 택했다(수용 기준이 명시한 "페이지네이션 또는 무한스크롤" 중 더 단순하고 테스트하기 쉬운 쪽).
