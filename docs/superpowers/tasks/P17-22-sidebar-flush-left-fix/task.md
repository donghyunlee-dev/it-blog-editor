# P17-22: 사이드바를 다시 항상 왼쪽에 고정 — task

## 배경
- 사용자가 병합된 P17-18(워크스페이스 전체 최대폭 1800px + 중앙 정렬)을 실제
  화면에서 보고 스크린샷과 함께 리포트: "LNB 왼쪽 공간 뭘까? 뭘 수정했길래
  이럴까." 사이드바(LNB) 왼쪽에 원인을 알 수 없는 빈 공간이 보인다는 것.
- 확인 질문으로 두 가지를 짚었다:
  1. 오른쪽에도 대칭적인 여백이 있는지 → **아니요, 오른쪽은 본문/목차가 실제로
     끝까지 꽉 차 있음**(비대칭 — 원래 의도한 "워크스페이스 전체를 대칭으로
     가운데 정렬"과도 다른, 실질적인 회귀).
  2. "사이드바까지 포함해서 가운데로 모이는" 동작 자체를 유지할지, 사이드바는
     항상 왼쪽에 고정하고 본문+목차만 가운데 정렬할지 → **"사이드바는 항상
     왼쪽에 고정"을 선택**(VS Code/Slack/Notion처럼 탐색 패널은 화면 왼쪽 끝에
     붙어 있는 게 사용자 기대와 맞는다는 이유).
- 결론: P17-18의 "워크스페이스 전체(사이드바 포함) 중앙 정렬" 설계 자체를
  되돌리고, "넓은 모니터에서 본문 좌우로 커지는 빈 공간"이라는 원래 목표는
  본문+TOC 묶음에만 최대폭을 씌우는 것으로 좁혀서 해결한다.

## 수용 기준 (Acceptance Criteria)
- [x] 사이드바는 화면(뷰포트) 폭과 무관하게 항상 왼쪽 끝에 고정된다 — 사이드바
      왼쪽에 어떤 여백도 생기지 않는다.
- [x] 본문+TOC는 여전히 최대폭이 있어, 아주 넓은 화면에서 본문 좌우로 무한정
      커지는 빈 공간이 생기지 않는다(P17-18의 원래 목표 유지) — 다만 이제
      "본문+TOC 묶음"에만 최대폭을 적용하고, 사이드바는 그 계산에서 제외한다.
- [x] 이 묶음이 최대폭보다 좁은 일반적인 화면(대부분의 실사용 해상도)에서는
      기존(P17-18 이전)과 완전히 동일하게 보인다 — 회귀가 이 기능 자체가 아니라
      "사이드바까지 포함시킨 범위"에 있었으므로, 범위만 좁히고 핵심 목표는
      유지한다.
- [x] 사이드바 폭 조절 드래그가 다시 "커서 x좌표 = 폭"으로 정확히 동작한다
      (P17-18에서 도입했던 오프셋 계산은 더 이상 필요 없다).
- [x] 접힌 사이드바를 다시 펴는 버튼이 화면 왼쪽 끝 고정 위치(`fixed`)에 정확히
      나타난다.

## 결정이 필요한 사항
없음 — 사용자가 두 질문에 명확히 답해 방향이 확정됐다. 본문+TOC 묶음의 구체적인
최대폭 값(1300px)은 Wide mode 본문(1200px)+거터를 넉넉히 담는 값으로 직접
정했다(WIDTH_STEP과 같은 선례 — 구현 디테일 판단).
