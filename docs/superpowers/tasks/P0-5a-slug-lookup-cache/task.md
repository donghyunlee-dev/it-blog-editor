# P0-5a: slug 중복 검사 반복 비용을 캐시로 완화(즉시 완화책)

## 배경
2026-08-27 [프로덕션 준비도 감사](https://claude.ai/code/artifact/87302c07-68d6-42ed-8712-9345547cb659)에서 P0로 지적된 항목. `findPublishedPageBySlug`(`src/lib/confluence/client.ts:375-411`)는 게시할 때마다 Space의 모든 페이지를 페이지네이션으로 순회하며, 페이지마다 **또** `getPageProperty`를 호출한다(N+1) — 문서 수가 늘어날수록 게시 요청이 선형으로 느려진다. `docs/product/data-spec.md:71`도 이미 "Space 내 문서 수가 크게 늘어나면 성능 재검토가 필요하다"고 밝힌 위험이다.

근본적인 구조 개선(색인 또는 Confluence CQL 검색 활용)은 [Issue #3](https://github.com/sfood-pioneer-1st/sfood-it-editor/issues/3)(P0-5b)에서 별도로 결정한다. 이 항목은 그 결정이 나오기 전까지 즉시 적용 가능한 완화책만 다룬다.

## 수용 기준 (Acceptance Criteria)
- [ ] 같은 Space에 대해 짧은 시간(TTL) 안에 여러 번 slug 검사가 일어나면, 두 번째부터는 Space 전체를 다시 스캔하지 않고 캐시된 결과를 쓴다.
- [ ] 이 프로세스가 직접 문서를 게시(publish)한 직후에는 캐시를 무효화해, 방금 자신이 쓴 slug를 스스로 못 알아채는 일이 없게 한다(같은 프로세스 안에서의 연속 게시는 항상 최신 상태를 본다).
- [ ] 캐시는 TTL이 지나면 자동으로 다시 스캔한다 — 무한정 오래된 데이터를 계속 쓰지 않는다.
- [ ] 기존 `findPublishedPageBySlug`/`publish.ts`의 동작(반환 타입, 호출 시그니처)은 그대로 유지한다 — 호출부를 바꾸지 않는다.

## 알려진 한계 (의도적으로 받아들이는 위험)
- 이 캐시는 **완전한 정확성을 보장하지 않는다.** TTL 안에서, 이 프로세스가 아닌 **다른** 프로세스/서버 인스턴스가 방금 새로 게시한 slug는 캐시가 알아채지 못해, 아주 좁은 시간 창에서 이론적으로 같은 slug가 중복 게시될 수 있다. TTL을 짧게(15초) 잡아 이 창을 최소화하지만 0으로 만들지는 못한다 — 완전한 해결은 P0-5b(구조적 재설계)의 몫이다.
- 이 프로젝트의 예상 사용자 규모("조직·다수(10명+)", architecture.md)와 게시 빈도를 고려하면 이 창에서 실제 충돌이 발생할 확률은 낮다고 판단했다. 만약 실사용에서 문제가 되면 TTL을 더 줄이거나 P0-5b를 앞당긴다.

## 결정이 필요한 사항
없음 — TTL 값(15초)은 "즉시 완화책"의 성격에 맞게 보수적으로(짧게) 잡은 기본값이며, 위 트레이드오프를 감수할 수 있는 범위라고 판단했다.

## 범위 밖
