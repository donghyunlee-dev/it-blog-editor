# P0-4b: 이미지 업로드 개수 제한

## 배경
2026-08-27 [프로덕션 준비도 감사](https://claude.ai/code/artifact/87302c07-68d6-42ed-8712-9345547cb659)에서 P0로 지적된 항목의 일부. `registerImage`(`src/lib/editor/images.ts`)는 MIME 타입만 검사할 뿐 업로드 개수에 제한이 없다. 최대 파일 **크기**(P0-4a)는 값 결정이 필요해 [Issue #2](https://github.com/sfood-pioneer-1st/sfood-it-editor/issues/2)로 분리했고, 이 항목은 값 결정이 필요 없는 **개수** 제한만 다룬다.

코드를 다시 확인한 결과, 드래그앤드롭(`handleDrop`)과 붙여넣기(`handlePaste`)는 이미 `event.dataTransfer?.files?.[0]`/`event.clipboardData?.files?.[0]`로 **첫 번째 파일 하나만** 처리하고 있어(`src/components/editor/RichTextEditor.tsx:421,444`), "1회 처리량"은 사실상 이미 1개로 제한돼 있다. 실제로 비어 있는 것은 **문서 하나에 누적으로 몇 장까지 넣을 수 있는지**에 대한 상한이다 — 지금은 사용자가 계속 붙여넣으면 문서 하나에 이미지가 무한정 쌓일 수 있다.

## 수용 기준 (Acceptance Criteria)
- [ ] 문서(TipTap doc)에 이미 포함된 이미지 노드 수가 상한(30장)에 도달한 상태에서 드래그앤드롭/붙여넣기/슬래시 메뉴 "이미지"로 새 이미지를 추가하려 하면, 업로드 요청 자체를 보내지 않고 안내 토스트를 띄운다.
- [ ] 상한 미만이면 기존과 동일하게 정상 업로드된다.
- [ ] 세 진입점(드래그앤드롭·붙여넣기·슬래시 메뉴) 모두 동일한 상한을 공유한다.

## 결정이 필요한 사항
없음 — 상한 값(30장)은 사내 기술 문서 용도로 넉넉하게 잡은 기본값이며, 이 값 자체는 안전을 해치지 않는 UX 가드레일이라 GitHub Issue로 결정을 받을 필요가 없다고 판단했다(값을 더 조정해야 하면 언제든 상수 하나만 바꾸면 된다).

## 범위 밖
- **서버 측 강제**는 다루지 않는다 — 이 제한은 "문서 하나에 이미지가 통제 없이 계속 쌓이는 것"을 막는 UX 가드레일이지 보안 경계가 아니다(진짜 보안/비용 경계는 P0-4a의 파일 크기 제한 쪽이다). 서버가 저장 시점에 문서 JSON을 순회해 이미지 개수를 다시 검증하려면 별도의 서버 측 검증 계층이 필요해 이번 범위를 벗어난다고 판단했다 — 필요해지면 별도 항목으로 논의한다.
- 이미 상한을 넘겨 저장된 기존 문서(마이그레이션 이전 데이터)에 대한 처리 — 실사용 데이터가 없어 해당 없음.
