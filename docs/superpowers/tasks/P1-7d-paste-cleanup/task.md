# P1-7d: Word/Google Docs 붙여넣기 서식을 정제하는 로직을 추가한다

## 배경
2026-08-27 [프로덕션 준비도 감사](https://claude.ai/code/artifact/87302c07-68d6-42ed-8712-9345547cb659)에서 지적된 항목. 실제로 소스를 확인해보니 이건 단순한 "HTML이 지저분해 보인다" 수준의 문제가 아니라, **이미 내려진 제품 결정을 붙여넣기 경로가 조용히 우회하는 실제 버그**였다.

이 에디터는 글자색을 정해진 스와치로만 고르게 제한해 뒀다(`RichTextEditor.tsx`의 `TEXT_COLOR_SWATCHES` 도입 배경 주석 — "브라우저 기본 컬러 피커를 없애서 브랜드 톤과 무관한 임의 색을 못 고르게 했다"). 그런데 `@tiptap/extension-text-style`의 `TextStyle` 마크는 `parseHTML`에서 `style` 속성이 있는 아무 `<span>`이든 매치하고(`!element.hasAttribute("style")`이면만 거부), `Color` 확장은 그 `style`에서 `color` 값을 그대로 읽어들인다(`node_modules/@tiptap/extension-text-style/dist/index.cjs` 확인). Word·Google Docs는 텍스트 조각마다 `<span style="color:...; font-family:...">`를 촘촘히 붙여 내보내므로, 붙여넣기를 그대로 두면 임의의 외부 색상·폰트가 스와치 제한을 무시하고 문서에 그대로 들어온다.

## 수용 기준 (Acceptance Criteria)
- [ ] 외부(Word, Google Docs, 다른 웹페이지 등 어디서든)에서 붙여넣은 콘텐츠의 인라인 `style` 속성이 문서에 반영되지 않는다 — 특히 임의의 글자색·폰트가 새어 들어오지 않는다.
- [ ] 붙여넣은 텍스트의 내용 자체(글자)는 그대로 보존된다 — 서식만 제거하고 텍스트는 잃지 않는다.
- [ ] 같은 세션 안에서 이 에디터 자신의 콘텐츠를 복사해 다시 붙여넣는 일반적인 경우는 영향받지 않는다(ProseMirror가 브라우저 클립보드 HTML 재파싱 없이 원본 슬라이스를 그대로 쓰는 내부 최적화 경로를 타므로 자연히 해당 없음).
- [ ] 기존 붙여넣기 동작(이미지 붙여넣기, 코드블록의 VS Code 붙여넣기 감지 등)에 회귀가 없다.

## 결정이 필요한 사항
없음 — 출처(Word인지 Google Docs인지 그냥 다른 웹사이트인지)를 감지해서 다르게 처리하지 않고, 인라인 `style` 속성을 출처와 무관하게 전부 제거하는 쪽으로 정했다. 이 에디터의 스키마 자체가 애초에 임의의 인라인 스타일을(정해진 스와치 밖의 색상 등) 지원하지 않으므로, 어느 출처에서 오든 같은 문제이고 같은 해법이 맞다 — 세분화된 출처 감지는 복잡성만 늘리고 실익이 없다고 판단했다.

## 범위 밖
- Word가 내보내는 `mso-list` 기반의 사이비 리스트(`<p class="MsoListParagraph">`)를 진짜 `<ul>`/`<ol>` 구조로 재구성하는 것 — Word의 리스트 인코딩 방식을 별도로 해석해야 하는 훨씬 큰 작업이라 범위 밖으로 둔다. 지금 정제로도 리스트처럼 보이는 텍스트 자체는 그대로 붙여넣어지고, 스타일만 제거될 뿐이다(리스트 구조 재현은 안 됨).
- `class` 속성 제거 — 이 프로젝트 스키마는 어떤 마크/노드도 클래스명 기반으로 매치하지 않으므로, Word의 `MsoNormal` 같은 클래스가 남아있어도 실제 렌더링에는 영향이 없다. 제거해도 되지만 굳이 할 이유가 없어 범위 밖으로 둔다.
- 붙여넣은 링크(`<a href>`)의 위험한 스킴(예: `javascript:`) 검사 — 이미 `@tiptap/extension-link`가 `isAllowedUri`로 파싱 시점에 자체 검증하고 있음을 소스로 확인했다(`node_modules/@tiptap/extension-link` 확인). 이번 작업과 무관한, 이미 해결된 사안이다.
