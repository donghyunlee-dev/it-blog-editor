# P1-3: `confluenceRequest`에 429/5xx 대상 재시도·지수 백오프를 추가한다

## 배경
2026-08-27 [프로덕션 준비도 감사](https://claude.ai/code/artifact/87302c07-68d6-42ed-8712-9345547cb659)에서 P1로 지적된 항목. `confluenceRequest`(`src/lib/confluence/client.ts:26-54`)는 이 프로젝트가 Confluence Cloud REST API를 호출하는 유일한 저수준 창구이지만, 현재는 응답이 실패(`!response.ok`)이면 원인을 가리지 않고 즉시 `ConfluenceApiError`를 던진다. Confluence 쪽의 일시적인 레이트리밋(429)이나 순간적인 5xx 장애까지 그대로 사용자에게 실패로 노출되어, 다시 시도하면 성공했을 요청까지 불필요하게 막고 있다.

관련 문서: [prd.md의 Phase 4 P1-3 체크리스트](../../../product/prd.md), [data-spec.md](../../../product/data-spec.md)(별도 저장소 없음 — 이 항목은 순수 네트워크 계층 보강)

## 수용 기준 (Acceptance Criteria)
- [ ] GET(멱등) 요청이 429 또는 5xx 응답을 받으면, 최대 3회까지 지수 백오프(+ jitter)로 자동 재시도한다.
- [ ] 429 응답에 `Retry-After` 헤더(초 단위)가 있으면 지수 백오프 계산값 대신 그 값을 우선 사용한다.
- [ ] 재시도를 모두 소진한 뒤에도 실패하면 기존과 동일한 `ConfluenceApiError`(상태 코드·메시지 포맷 동일)를 던진다 — 호출부(`documents.ts` 등 도메인 계층)의 에러 처리 방식을 바꾸지 않는다.
- [ ] 429/5xx가 아닌 4xx(400/401/403/404/409 등)는 재시도하지 않고 즉시 던진다 — 도메인 계층이 404/409를 구분해 쓰는 기존 동작에 영향 없어야 한다.
- [ ] GET이 아닌 요청(POST/PUT/DELETE)은 429/5xx를 받아도 재시도하지 않는다(근거는 아래 "결정이 필요한 사항" 참고).
- [ ] 재시도 사이에 실제로 지연이 발생하는지, 그리고 지연 없이 테스트가 느려지지 않는지를 fake timer로 검증한다.
- [ ] 기존 `client.test.ts`의 모든 테스트가 회귀 없이 통과한다.

## 결정이 필요한 사항
없음. 다만 두 가지는 "즉시 조치" 성격에 맞춰 이 작업 안에서 보수적인 기본값으로 직접 정했다(P0-5a의 TTL 값 결정과 같은 방식 — 검증 가능한 값이고 나중에 실사용 데이터로 조정 가능하므로 GitHub Issue 없이 진행):
- **재시도 대상을 GET으로 한정한 이유**: Confluence Cloud API에는 idempotency key가 없다. POST(`createPage`, `addLabels` 등)나 PUT/DELETE가 실제로는 서버에 반영됐는데 응답만 유실되어 5xx로 보인 경우, 재시도하면 페이지 중복 생성·라벨 중복 추가 같은 부작용이 생길 수 있다. 읽기 전용 GET만 안전하게 재시도할 수 있다고 판단했다 — `updateDocument`의 버전 검사(P0-3)와 같은 결로, "완전한 재시도"보다 "부작용 없는 범위의 재시도"를 택했다.
- **횟수·백오프 값(최대 3회, 지수 백오프 + jitter)**: 표준적인 기본값이며, 사용자를 오래 기다리게 하지 않는 선(총 대기 시간 수 초 이내)에서 순간적인 장애를 흡수하는 데 목적이 있다. 근거가 되는 감사 리포트도 구체적인 횟수를 지정하지 않았다.

## 범위 밖
- `uploadAttachment`(이미지 업로드, `src/lib/confluence/client.ts:347`)는 `confluenceRequest`를 쓰지 않는 별도의 raw `fetch` 호출이라 이 작업에서 다루지 않는다. 대용량 파일 업로드를 자동 재시도하면 사용자가 체감하는 대기 시간이 크게 늘어날 수 있어 별도 검토가 필요하다.
- Slack 웹훅 자체의 재시도/폴백은 P1-4b에서 별도로 다룬다.
- 사용자 요청 자체에 대한 레이트리밋(우리 서버가 클라이언트를 제한하는 것)은 P1-5(🔶, Issue #5)에서 별도로 다룬다 — 이 항목은 반대로 우리가 Confluence의 레이트리밋을 만났을 때의 대응이다.
