# P1-6c: slug 형식(허용 문자)을 서버에서 검증한다

## 배경
2026-08-27 [프로덕션 준비도 감사](https://claude.ai/code/artifact/87302c07-68d6-42ed-8712-9345547cb659)에서 지적된 항목. `publish.ts`의 `validateAndComposeViewers`는 현재 slug가 비어있는지만 검사(`!meta.slug`)할 뿐 형식(허용 문자)은 전혀 검증하지 않는다.

이 slug는 `publicSlug`(`${slug}-${내부고유키}`)로 그대로 조합돼 Tech Blog 등 뷰어의 **공개 URL 경로 세그먼트**로 쓰인다(P0-5b). 실제로 (P1-11) `slug: "/root"`처럼 슬래시가 포함된 값이 저장된 사례가 실제 인스턴스(pageId `212959235`)에서 발견됐다 — 이 값은 URL 경로 세그먼트 하나에 들어가야 하는데 슬래시가 섞이면 라우팅 자체가 깨진다. 이 항목이 그 문제를 구조적으로 막는다.

## 수용 기준 (Acceptance Criteria)
- [ ] `validateAndComposeViewers`(`publish.ts`)가 slug 형식을 검증해, 표준 kebab-case 규칙(소문자 영숫자와 하이픈만, 하이픈으로 시작/끝 불가, 하이픈 연속 불가)을 벗어나면 `ValidationError`(400)를 던진다.
- [ ] `/`, 공백, 대문자, 언더스코어 등 규칙을 벗어나는 값은 모두 거부된다 — 특히 P1-11에서 실제로 발견된 `"/root"` 같은 값이 이제는 게시 시점에 거부된다.
- [ ] 규칙을 만족하는 일반적인 slug(예: `my-first-post`, `react-19-review`)는 기존과 동일하게 정상 처리된다.
- [ ] 빈 값 검증(기존 "필수입니다" 메시지)은 형식 검증보다 먼저 그대로 유지된다 — 빈 문자열에 형식 검사를 적용해 다른(혼란스러운) 에러 메시지가 나가지 않게 한다.

## 결정이 필요한 사항
없음 — 여기서 정하는 "허용 문자" 규칙은 서비스 정책이 아니라 "URL 경로 세그먼트 하나로 안전하게 들어가야 한다"는 기술적 제약이다. 채택한 규칙(소문자+숫자+하이픈, kebab-case)은 GitHub·Notion·일반 블로그 플랫폼의 slug 관례를 그대로 따른 것이라 이해관계자 결정이 필요 없다고 판단했다(P0-4b/P1-6a/P1-6b와 같은 근거로 GitHub Issue 없이 직접 정한다).

## 범위 밖
- 클라이언트(`PublishForm.tsx`)의 실시간 형식 안내(예: 입력 중 유효하지 않은 문자 강조) — 이번엔 서버 검증만 다룬다.
- slug 최대 길이 상한 — PRD 항목(P1-6c)이 "허용 문자"만 명시하고 있어 범위 밖으로 둔다. 필요해지면 별도 항목으로 추가한다.
- 실제 인스턴스에 이미 저장된 `"/root"`(pageId `212959235`, P1-10/P1-11) 값을 수동으로 정리하는 작업 — 이 문서는 이미 Space 최상위로 유실된 상태(P1-10)라 별도 정리가 필요하며, 이번 작업의 범위 밖이다.
