# P1-6c: slug 형식(허용 문자)을 서버에서 검증한다 — 구현 결과 보고서

## 구현 내용
`src/lib/editor/publish.ts`의 `validateAndComposeViewers`에 slug 형식 검증을 추가했다.

- **패턴**: `SLUG_PATTERN = /^[a-z0-9]+(-[a-z0-9]+)*$/` — 소문자 영숫자와 하이픈만 허용, 하이픈으로 시작/끝 불가, 하이픈 연속 불가(표준 kebab-case slug 관례).
- 빈 값 검사("필수입니다") 다음 순서로 형식 검사를 수행한다 — 순서를 바꾸지 않아 빈 문자열에 형식 위반 메시지가 잘못 나가는 일이 없다.
- 위반 시 기존과 동일하게 `ValidationError`(400)를 던진다.
- 이 slug는 그대로 `publicSlug`(`${slug}-${내부고유키}`)로 조합돼 Tech Blog 등 뷰어의 공개 URL 경로 세그먼트가 되므로(P0-5b), 실제로 발견된 `"/root"`(P1-11, pageId `212959235`) 같은 슬래시 포함 값이 이제는 게시 시점에 거부된다.

## 자체 검토 (Self-Review)
### 긍정 사항
- 채택한 문자 규칙(kebab-case)의 근거를 추측이 아니라 "URL 경로 세그먼트 하나로 안전해야 한다"는 기술적 제약과 업계 관례로 명시했다.
- P1-11에서 실제 인스턴스에서 발견된 구체적 위반 사례(`"/root"`)를 테스트 케이스로 그대로 재현해, 이 검증이 실제 문제를 막는지 직접 확인했다.
- 범위를 PRD 항목이 명시한 "허용 문자"로만 좁혀, slug 최대 길이 등 요청받지 않은 검증을 추가하지 않았다(과잉 설계 방지).

### 주의사항
- 클라이언트(`PublishForm.tsx`)는 형식을 사전에 안내하지 않는다 — 사용자가 잘못된 slug를 입력하고 blur/게시 시도 시에야 서버 400 메시지로 알게 된다. 필요해지면 후속 UX 개선으로 다룬다(범위 밖으로 명시).
- 이미 실제 인스턴스에 저장된 위반 사례(`"/root"`)는 이번 검증이 신규 저장만 막을 뿐 소급 정리하지 않는다 — 해당 문서 자체가 P1-10으로 이미 유실 상태라 별도 정리가 필요하다.
