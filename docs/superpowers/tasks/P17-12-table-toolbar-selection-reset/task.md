# P17-12: 표 툴바 버튼이 커서 선택을 되돌려버리는 문제 (사용자 추가 요청)

## 배경
- 원래 Phase 17 목록(P17-1~P17-8)에는 없던 항목이다 — P17-7(표 행/열 삭제 확인
  일관성) 작업 중 사용자가 실사용으로 겪은 문제를 지적해 이어서 추가했다.
- 사용자 지적 1: "8개의 로우를 체크해 놓고 7번에 포커스를 두고 행추가 위, 아래를
  해도 1번으로 이동해서 추가가 돼." → 이 세션의 Browser pane/Playwright 자동화
  테스트로는 재현되지 않았으나, 사용자가 실제 브라우저에서 직접 원인을 찾아냈다:
  "테이블 위에 툴바를 클릭하면 마우스 포인트가 테이블 첫번째로 이동하면서 행이
  무조건 첫번째 행 기준으로 위/아래 생겨. 마우스 포커스를 최대한 위쪽을 클릭하면
  정상 동작되네."
- 사용자 지적 2: "2개의 컬럼을 드래그하면 병합 버튼이 활성화가 돼. 하지만 누르면
  아무 변화가 없어." → 사용자가 스스로 진단: "병합/해제도 동일한 문제야. 누르는
  순간 첫번째 행이 클릭이 되면서 포커스가 이동되니까 아무것도 안되는 거야."
- 사용자 지적 3(같은 스레드, 별개 발견): "근데 내가 여러 행을 잡으면 백그라운드
  색이라도 변경을 해줘야 선택이 되었다는 걸 알텐데 그런게 없어." — 셀 다중 선택 시
  시각적 피드백이 전혀 없다.

## 원인 분석
- `TableToolbarButton`(`RichTextEditor.tsx`)의 버튼은 표 노드뷰의 `contentDOM`
  (tbody) 밖, `<table>` 바로 앞에 꽂히는 툴바 슬롯 안에 있다(`TableToolbar`/
  `createStickyTableView` 참고). `onClick`만 있고 `onMouseDown`으로 기본 동작을
  막지 않아, 버튼을 누르는 mousedown 시점에 브라우저가 기존 에디터 선택(사용자가
  마지막으로 클릭해 둔 행)을 표의 첫 번째 셀 쪽으로 되돌려 버렸다 — 리치 텍스트
  에디터에서 툴바 버튼에 `onMouseDown={e => e.preventDefault()}`를 안 하면 흔히
  겪는 잘 알려진 문제다. 그 뒤에 실행되는 `onClick`의 `addRowBefore`/`addRowAfter`/
  `mergeCells`/`splitCell`/`deleteRow`/`deleteColumn` 등은 이미 망가진(1행으로
  재설정되거나 CellSelection이 사라진) 선택을 기준으로 동작해, "항상 1행 기준으로
  추가된다"/"병합 버튼은 활성화되는데 눌러도 아무 일도 안 일어난다"는 두 증상이
  같은 근본 원인에서 나왔다.
- 이 세션의 Browser pane(헤드리스 Chromium)과 실제 Playwright 자동화 모두 이
  문제를 재현하지 못했다 — 합성 마우스 이벤트가 실제 하드웨어 마우스 입력과
  달리 이 특정 브라우저 선택-되돌림 동작을 트리거하지 않는 것으로 보인다. 사용자가
  실제 브라우저에서 직접 재현·진단했다.
- 셀 다중 선택 시 배경색이 안 보이는 문제는 별개 원인이다 — `prosemirror-tables`가
  선택된 셀에 `selectedCell` CSS 클래스를 공식적으로 붙여 주는데(라이브러리가 의도한
  스타일링 훅), 이 프로젝트에 그 클래스에 대응하는 CSS가 아예 없었다.

## 수용 기준 (Acceptance Criteria)
- [x] 표 툴바의 어떤 버튼(행/열 추가·삭제, 병합, 분할, 표 삭제)을 클릭해도 클릭
      직전의 에디터 선택(커서 위치 또는 셀 범위 선택)이 그대로 유지된 채 명령이
      실행된다.
- [x] 여러 셀을 드래그/Shift+클릭으로 선택하면 배경색으로 선택 상태가 시각적으로
      드러난다.

## 결정이 필요한 사항
없음 — 둘 다 명확한 버그이며 값·방식을 따로 정할 필요가 없다.

## 범위 밖

  사용자가 실제 브라우저에서 이미 원인을 확정했으므로 재현 자체보다 수정과 회귀
  방지 테스트에 집중한다.
